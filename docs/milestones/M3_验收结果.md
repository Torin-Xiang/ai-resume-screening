## 交付内容

1. `core/rubric_gen.py`：JD → 评分卡草稿（三类维度 + definition + 正反例 + rule 建议 + 权重建议）。
2. **合规兜底**：模型偶尔会写出"年龄 30 岁以下""男性优先"这类维度 →
   生成时**剔除该维度并记账**（`dropped`），不让整份评分卡失败；剔除数量写入 `notes`。
3. **版本化**：默认版本号 `YYYY-MM-DD-draft`，可用 `--version` 指定业务版本；
   结果表与 `run.json` 都记录所用版本（§4.4）。
4. CLI：`rubric new` / `rubric validate` / `rubric show`。

## 与方案的偏差

- 方案 §5.2 的 `hard_filters` 示例是纯自然语言维度。本实现给硬门槛增加了可选的 `rule` 字段：
  **能规则化的硬门槛（学历/年限/地点/专业/跳槽频次）指定 rule 后由规则引擎判定**（§4.2 优先路径），
  无法规则化的软性口径仍由 LLM 判定。这是为了满足 §4.2 与 §5.2 的一致性，不是新增功能。
  未指定 rule 时，`rubric validate` 会给出"建议指定 rule"的提示。

## 阻塞项

1. **无 `DASHSCOPE_API_KEY`** → 未做真实 JD 生成。
2. **HR 维度认可度未评审**（方案 §8 M3 的验收标准本身是主观项）：
   需业务方对 `rubric new` 产出的维度逐条确认，并补充/改写 `definition` 与正反例。
   建议做法：拿 1 份真实 JD 生成 → HR 编辑 → 作为团队基线评分卡存入 `rubrics/`。
