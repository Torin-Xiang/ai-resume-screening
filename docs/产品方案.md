## 1. 目标与核心假设

面向 HR 招聘场景的简历初筛工作流。MVP 阶段只验证一个假设：

> **AI 初筛能否真正节省 HR 的时间，并且淘汰结论 HR 敢信。**

两个要点缺一不可。只快不准 = 没人用；只准不快 = 不值得用。因此 MVP 必须端到端跑通（丢一个文件夹进去 → 出一张能直接用的 Excel），任何一环缺失都无法验证假设。

**成功标准（MVP 验收）**
- 一份简历从进入到出结果，明显快于人工初筛
- HR 对淘汰结论的认可率足够高，愿意采用
- 每条淘汰结论都能追溯到简历原文

## 2. MVP 范围

### 2.1 必做（P0）

| # | 环节 | 内容 | 备注 |
|---|---|---|---|
| ① | 解析 | PDF → 纯文本，按坐标块重排 | 最大工程风险点，见 §9 |
| ② | 结构化提取 | 9 项核心字段 + 每项原文溯源 | 见 §6.1 |
| ③ | 评分卡 | 从 JD 生成维度草稿，HR 可编辑，存 JSON | 见 §5 |
| ④ | 双层评估 | 规则判硬门槛 + LLM 只做软性判断 | 见 §4.2 |
| ⑤ | 导出与复核 | Excel（排名/分数/理由/证据/联系方式/原文件路径）+ 判定回写 | 回写数据是 v2 唯一改进依据 |

### 2.2 明确不做（延后至 v1 及以后）

- Web UI、登录、权限模型
- 向量库 / 语义搜索
- **自动发拒信**（发错撤不回，MVP 阶段必须人工发送）
- 面试安排、题库生成
- BI 看板、候选人画像
- 模型微调、权重自动学习（见 §4.4）
- 多 JD 管理台

## 3. 用户工作流

```
准备 JD 与简历文件夹
        ↓
rubric new --jd "岗位 JD 文本"     # 生成评分卡草稿
        ↓
人工编辑评分卡 JSON（定义口径、调权重）
        ↓
screen --rubric rubrics/xxx.json --input resumes/
        ↓
产出 Excel：排名 / 分数 / 命中维度 / 证据引用 / 联系方式 / 原文件路径
        ↓
HR 人工复核，判定回写（通过 / 淘汰 / 待确认）
```

业务口径变化时：**只改评分卡 JSON，重新执行 `screen`，不重新解析简历。**

## 4. 架构与关键设计决策

### 4.1 分层：变的东西与不变的东西分开

```
CLI 薄壳  ──→  核心库 core（纯逻辑，不认识 CLI）  ──→  适配器
                                                    ├ 解析器（PDF / docx 可加）
                                                    ├ 模型客户端（qwen / DeepSeek 可换）
                                                    └ 导出器（Excel / CSV / 飞书）
```

- **不变**：简历解析 + 字段提取 → 结果缓存为中间 JSON
- **变**：评分卡（硬门槛 / 加分项 / 减分项 + 权重）

**新增功能 = 加适配器，不动核心。**

### 4.2 决策一：硬门槛用规则，不用 LLM

- **决策**：学历、工作年限、专业、地点、跳槽频次等布尔判断，全部由规则判定；LLM 只负责规则判不了的部分（岗位相关性、项目含金量、技能深度）。
- **理由**：规则成本为 0、准确率 100%、完全可解释；LLM 算"工作年限"这类会算错，且更贵。
- **代价**：规则需要维护一份配置，新增硬门槛要写代码注册。

### 4.3 决策二：每条结论必须带原文引用，区分「不满足」与「未提及」

- **决策**：所有判断必须引用简历原文片段；引不出来就承认"未提及"。简历未提及的项**不得直接淘汰**，标记为"待确认"。
- **理由**：这是 HR 敢不敢用的分水岭。无法追溯的结论等于黑箱，HR 不会采信，也有合规风险。
- **代价**：prompt 更复杂，输出 token 更多。

### 4.4 决策三：业务口径动态可变，评分卡外置为配置

- **决策**：评分卡是独立 JSON 文件，带 `schema_version` 与业务版本号；代码零改动即可切换筛选侧重。
- **理由**：业务方筛选侧重会动态变化，这是明确的现实需求。
- **配套**：①每次筛选结果记录所用评分卡版本，避免不同标准的结果混在一起无法对比复盘；②解析结果缓存，换侧重只重跑评分层，可低成本做 A/B 对比。
- **不做**：权重自动学习（用历史录用数据回归权重）。标注数据不足时学出来是噪声，HR 不会信；等人工复核数据攒够 200+ 条再评估。

### 4.5 决策四：合规红线（不可妥协）

**以下属性不得进入评分维度**：性别、年龄、婚育状况、籍贯、民族、健康状况、政治面貌。

- 依据：《就业促进法》及雇主品牌风险。
- 实施要求：模型容易从毕业年份反推年龄、从姓名推断性别，**必须在 prompt 中显式禁止**使用这些信号，并在输出校验层拦截。

### 4.6 决策五：判定口径靠自然语言定义，不靠布尔规则

像"必须有 AI 项目经验"这类条件，真正的难点不是配置，而是口径不清——做过微调算、调 API 算、写 prompt 算不算？口径不明会导致同一份简历每次判定结果不同，容易被误判为"模型不稳定"。

因此评分卡每个维度都包含三个字段：`definition`、`positive_examples`、`negative_examples`。业务改侧重时，改的是这几句话。

## 5. 评分卡设计

### 5.1 三类维度

| 类型 | 作用 | 计分方式 |
|---|---|---|
| `hard_filters` | 必须项 | 不满足即一票否决 |
| `bonus` | 加分项 | 权重 × 命中度，累加 |
| `red_flags` | 减分项 | 命中则扣分 |

### 5.2 示例

```json
{
  "schema_version": "1.0",
  "version": "2026-09-26-ai-must",
  "job_title": "AI 应用开发工程师",
  "hard_filters": [
    {
      "id": "ai_exp",
      "name": "AI 项目经验",
      "definition": "候选人须在项目中实际参与过 AI 能力的设计或交付，而非仅使用成品工具。",
      "positive_examples": ["独立训练或微调过模型", "搭建过 RAG 或 Agent 流程并上线"],
      "negative_examples": ["仅调用 ChatGPT 辅助写作", "课程作业级别的 demo"]
    }
  ],
  "bonus": [
    { "id": "bigtech", "name": "大厂经历", "weight": 10 },
    { "id": "edu211", "name": "211/985 学历", "weight": 5 }
  ],
  "red_flags": [
    { "id": "job_hop", "name": "平均在职时长 < 1 年", "penalty": 8 }
  ]
}
```

### 5.3 CLI 子命令

- `rubric new --jd "..."` — 从 JD 生成评分卡草稿
- `rubric edit` — 编辑（或直接手改 JSON）
- `screen --rubric rubrics/xxx.json --input resumes/` — 执行筛选

## 6. 数据结构与接口约定

### 6.1 `ResumeDocument`（核心中间结构，用 pydantic 定义）

9 项核心字段：姓名、联系方式、学历、学校、专业、工作年限、现公司、现岗位、技能。

每项附 `evidence`（原文片段）与 `source`（出处定位）。新增字段一律可选（默认 `None`），保证向后兼容。

**该结构尽早定型**——后续所有模块都依赖它，反复改动会波及全项目。

### 6.2 标识与缓存

- `resume_id`：简历文件的内容 hash（内容不变则不重复解析）
- `run_id`：每次筛选运行唯一标识
- 解析结果缓存为中间 JSON，换评分卡重跑时不重复解析

### 6.3 LLM 调用

所有 prompt 走统一封装入口（含重试、限流、成本记录）。**禁止各模块各自裸调 SDK**，否则后期无法统一换模型与统计成本。

## 7. 技术栈

| 用途 | 选择 | 说明 |
|---|---|---|
| 语言 | Python 3.13（托管版 + venv） | 若 PyMuPDF wheel 不支持则退 3.12.4 |
| PDF 解析 | PyMuPDF | 提供坐标块，支持分栏重排 |
| 数据结构 / 输出校验 | pydantic v2 | 强制模型输出合规 JSON 并自动重试 |
| LLM 调用 | openai SDK | 走通义千问 DashScope 兼容端点，便于换模型 |
| Excel 导出 | openpyxl（+ pandas） | 精细控制样式、列宽、冻结首行 |
| CLI | typer | |
| 配置 / 重试 | python-dotenv、tenacity | API key 存 `.env` |
| 测试 | pytest | |

**为何选 Python**：主要不是"AI 都用 Python"，而是赢在两件真正难的事上——①中文 PDF 版式解析生态最强（Node 的 pdf-parse 只提文本不带坐标，做不了分栏重排）；②pydantic + structured outputs 是"每条结论带原文引用"原则的落地工具。

**已知代价**：分发较麻烦（给非技术同事用需打包或内网部署）；动态语言重构安全性弱于 TS，靠 pydantic + mypy + 测试补偿；GIL 不构成瓶颈（瓶颈是 LLM 网络 IO）。

| 里程碑 | 内容 | 验收标准 |
|---|---|---|

## 9. 风险登记

| 风险 | 等级 | 说明与应对 |
|---|---|---|
| **PDF 版式千变万化** | 高 | 最大风险点。解析器必须是纯函数（文件路径 → `ResumeDocument`），不掺评分逻辑与全局状态，否则加特例时会失控 |
| 扫描件 / 图片型 PDF | 中 | 解析质量自检：文本过短或中文占比异常 → 标记"需人工处理"，不送入模型 |
| 判定口径不清 | 中 | 靠 `definition` + 正反例定义，见 §4.6 |
| 合规违规 | 高 | 敏感属性不入评分维度，prompt 显式禁止，输出校验层拦截 |
| 个人信息泄露 | 中 | **脱敏简历样本不得进 Git**；测试 fixture 放本地目录并 gitignore |

## 10. 已知技术债（MVP 主动承担）

- 单进程 CLI → 将来要 Web / 多人用，需换异步任务队列
- 单 JD → 多岗位并行需要 `job_id` 概念（已预留 `run_id`，迁移成本低）
- 本地 JSON 存储 → 历史追溯与协作需换 SQLite
- 无权限模型 → 多人使用需补
