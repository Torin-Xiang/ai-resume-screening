## 1. 为什么推翻 v0.1

v0.1 的模型是「跑批任务」：写 JD → 生成评分卡 → 跑一批 → 出 Excel。它错在四件事：

1. **把持续工作建模成了一次性任务。** 一个岗位在招两周，简历陆续进来。跑批意味着每来一份简历就要重跑一轮、重新打开一次 Excel。而 HR 的真实状态是"一边收简历一边看人"。
2. **步骤多、门槛高。** 要记命令、要管目录结构、要手改 JSON。这些对 HR 来说全是**额外的活**，不是省下来的活。工具的启动成本一旦超过它省下的时间，就没有意义。
3. **结果不在看得见的地方。** Excel 是快照，不是常驻视图。谁被新加了、排名怎么变的，HR 不知道。
4. **批量思维带来错误的默认动作。** 跑批天然要求"先凑齐一批再跑"，而真实场景需要"来一份看一份"。

**结论：判断内核是对的，装错了外壳。** v0.1 里那些关于判断质量的设计（硬门槛用规则、结论带证据、未提及不淘汰、合规红线）全部继承。

## 2. 产品定位

> 把「逐份看简历」变成「看排序结果」。

**产品的基本单位不是"一次筛选任务"，而是"一个在招岗位"。**

每个岗位是一个持续存在的工作台：有 JD、有筛选标准、有不断增长的简历池、有实时更新的优先级排名。HR 打开产品看到的是"我手上这几个岗位现在什么情况"，而不是"我要发起一次筛选"。

### 2.1 为什么做成产品（而非直接用 AI 对话）

这一条必须写清楚，因为它决定了哪些需求是**真需求**、哪些可以妥协。

直接用 AI 对话也能做筛选，而且单次操作可能更省事。之所以要做成产品，是**两个理由**：

| 理由 | 含义 | 对设计的约束 |
|---|---|---|
| **① 可分享** | 一次验证过的筛选流程，可以给其他 HR 同事用，不需要他们各自去摸索提示词 | 必须是**网页**形态（能通过链接访问），不能是本地脚本或桌面程序 |
| **② 稳定** | 不像对话那样每次结果可能不同；同一批简历、同一套标准，今天和下周跑出来必须一致，且结论有据可查 | 标准必须版本化、判定必须带原文证据、禁止模型自由发挥 |

**"更快"不是产品存在的理由，是产品的下限。** 如果等待时间长到还不如直接对话，产品就失去了意义——所以速度是**门槛**（见 §7），不是卖点。这个定位的转变很重要：它意味着我们**不需要**为了快而牺牲准确率或可解释性，但也**绝不能**慢到让用户觉得不如去开个对话框。

### 2.2 产品边界（明确不做的事）

**一次评估 = 一个 JD + 一批 HR 指定的简历。** 仅此而已。

- **JD 由 HR 提供，简历由 HR 挑选。** 产品不负责去简历库捞人，不做候选人库管理，不做渠道对接。
- **不判断"哪个候选人该投哪个岗位"。** 简历与岗位的对应关系完全由 HR 决定。同一份简历要不要同时给两个岗位评估，是 HR 的操作选择，产品不介入。
- **不做跨岗位的候选人合并与去重。** 那不是产品的问题，是 HR 自己的判断。
- **不同岗位互不影响。** 每个岗位（即用户视角的"一个项目 / 一个对话框"）有独立的标准、简历池与排名，彼此隔离。

## 3. 核心用户与场景

- **用户**：一线招聘 HR。同一时间手上 3–10 个在招岗位，每天面对几十到几百份简历。
- **场景**：简历从多渠道陆续投进来。HR 的目标不是"看完所有简历"，而是**不漏掉该看的人、不在明显不合适的人身上花时间**。
- **成功的样子**：HR 打开岗位，只看「推荐」组的前十几份，其余靠排序结果放心跳过。

## 4. 设计原则（继承 v0.1，这是不可动的内核）

1. **硬门槛用规则，不用模型。** 学历、年限、专业、地点、跳槽频次是布尔判断——规则成本为 0、准确率 100%、完全可解释。模型只做规则判不了的部分。
2. **每条结论必须带原文引用，并区分「不满足」与「未提及」。** 未提及的项**不得据以淘汰**，标记为「待确认」交人工。引不出原文就承认不知道，禁止编造。
3. **合规红线。** 性别、年龄、婚育、籍贯、民族、健康状况、政治面貌不得进入评分维度。模型会从毕业年份反推年龄，需在判定与输入两侧都显式禁止。
4. **判定口径靠自然语言定义，不靠布尔规则。** 每个维度必须有 `definition` + 正反例。"有 AI 项目经验"真正的难点是口径不清（微调算不算？调 API 算不算？），不是配置。
5. **改标准必须可追溯，且不重跑解析。** 标准有版本号，每次结果记录所用版本；改标准后重排不重新解析简历。

| 1 | **多岗位并列** | 左栏岗位列表（带简历数），每个岗位独立的标准、简历池、排名 |

## 6. 关键交互约定

### 6.1 上传即处理，但结论"稳定后才呈现"

- 上传后立即进入处理队列，处理完自动进入排名，**不需要 HR 再点任何按钮**。
- 处理中显示「处理中」而**不显示分数**，避免呈现半成品结论。
- 解析失败（如扫描件无文本层）→ 明确标注「需人工」，并**必须给出出路**：原位置提供「粘贴文本」入口，HR 把简历内容粘进去，立刻参与排名。**绝不允许静默跳过**，否则 HR 会误以为系统看过并放过了这个人。
- **兜底方案的选择依据**：扫描件不做 OCR（成本高、中文版式准确率不稳），改用手工粘贴。理由是**对使用者更省事也更可靠**——粘贴一次即可，且粘进来的是 HR 亲自确认过的内容，不存在 OCR 识别错误导致误判还查不出来的情况。

### 6.2 一句话理由的硬约束

- 每条**最多一句话**（建议 30 字内），不允许糊成一段。
- 必须指向**具体标准 + 具体证据**，禁止"综合素质较好"这类无法验证的空话。
- 点开可看到：每条标准的判定结果 + 简历原文引用。

### 6.3 三分组，而不是一条纯排序

| 分组 | 含义 |
|---|---|
| **推荐** | 全部必须项已满足 |
| **待确认** | 有必须项在简历中「未提及」，无法确认是否满足 |
| **不推荐** | 有必须项明确「不满足」 |

**「待确认」必须与「不推荐」分开。** 若合并成一条排序，简历里没写到的人会被当成淘汰，这是最危险的误伤。待确认不是系统的无能，而是交给 HR 的待办清单。

### 6.4 改标准必须确认后生效

- 系统输出：**改了什么** + **对现有排名的影响** + 三个选择（确认生效 / 部分采纳 / 取消）。
- **不允许静默改标准。** HR 授权的是"帮我改"，不是"随便改"。
- 标准每次变更留版本，可回退。

### 6.5 合规红线在自然语言入口同样生效

如果用户说"把 35 岁以上的筛掉"或"已婚未育的先排除"，系统必须**拒绝执行并说明原因**，而不是照做。合规检查不能只加在结构化配置入口上。

## 7. 成功标准

**核心标准（决定产品有没有用）**

1. HR 对「推荐」组的认可率高 —— **唯一能证明产品有用的指标，需真实批次实测**。
2. **稳定性**：同一批简历 + 同一套标准，重复执行的结果一致；每条结论都能追溯到简历原文，且不出现原文里没有的内容。这是产品区别于"直接开个 AI 对话框"的根本所在。
3. **可分享**：链接发给另一位 HR，对方在自己的电脑上打开就能用，不需要装环境、不需要配 API key。

**门槛标准（达不到就失去产品意义）**

4. **上传到出结果的等待时间**：不能长到"还不如直接对话"。目标单份 ≤ 30 秒，需真实数据实测标定。
5. 改标准后立即重排，**不需要重新上传简历**。

**行为标准（说明产品真的被用起来了）**

6. HR 的工作方式从"逐份看简历"变为"只看推荐组的前 N 份"。
7. HR 愿意使用「同意 / 不同意」——这是系统以后变准的唯一输入来源。

## 9. 风险登记

| 风险 | 等级 | 说明与应对 |
|---|---|---|
| **处理速度** | 高 | 速度是**门槛**：一旦要等几分钟，用户就会觉得不如直接开个 AI 对话框，产品价值归零（§2.1）。需并发处理 + 解析缓存（已具备）+ 上传即入队不等批次 |
| **一句话理由退化** | 高 | 极易变成套话或幻觉。强制要求指向具体标准与原文证据，无证据不得输出结论 |
| **自然语言改标准被误改** | 中 | 用「改动清单 + 影响提示 + 确认」三道闸，且标准版本可回退 |
| **合规红线从自然语言入口泄漏** | 高 | 输入侧与输出侧都要拦截，不能只在配置侧校验 |
| **解析质量** | 高 | 中文 PDF 版式千变万化，仍是最大技术风险（细节见技术方案）。已有手工粘贴兜底作为出口 |
| **无法自行运行** | 中 | 产品化的理由之一是"可分享"，但若使用者需要自己装 Python 环境、自配 API key 才能用，分享就落空了。**必须做到：使用者只需一个链接和一次上传动作** |
| **HR 不信任大量「待确认」** | 中 | 产品上明确定位为"给你的待办清单"。若某必须项长期产生大量待确认，说明该标准的判定口径没写清楚，应引导 HR 修改口径，而不是放宽判定 |

## 10. 决策记录：原未决问题的答复

以下 5 项原为未决问题，已于 v1.1 由用户明确答复并固化。

| # | 原未决问题 | 决定 | 对设计的影响 |
|---|---|---|---|
| 1 | 产品载体形态 | **浏览器网页**。目标是先验证产品构想能否落地，不追求最终形态 | 决定了架构必须是"服务 + 浏览器界面"，不是本地脚本或桌面程序 |
| 2 | 单机单人 vs 小团队共享 | **先单机单人**；但因是网页形态，**必须保留"把链接给别人用"的能力** | 架构上不能是纯本地进程；数据存储要有明确的归属与落点（见技术方案） |
| 3 | 同一候选人投多个岗位如何呈现 | **不是问题。** 见 §2.2：一次评估 = 一个 JD + 一批 HR 指定的简历，对应关系由 HR 决定 | 删除了"跨岗位候选人合并去重"，产品不做自动关联 |
| 4 | 可接受等待时间阈值 | **速度是门槛，不是卖点**（§2.1）。一旦慢到不如直接对话，产品即失去意义 | 成功标准拆分为"核心标准 / 门槛标准"（§7）；风险登记的应对方式随之调整 |
| 5 | 扫描件兜底是否做手工粘贴 | **做，且升为 P0**；OCR 明确不做 | 网页形态下粘贴框成本极低，且比 OCR 更可靠（粘进来的是 HR 确认过的内容） |

### 10.1 仍然未决

1. **"可接受等待时间"的具体数值** —— 需真实批次实测标定。
2. **链接被他人打开后的数据归属** —— 当前按"看到同一份数据"实现：v1 定位是单机单人，分享链接的含义是"换个电脑继续用"，不是"多人协作"（多人协作见 §5.3 明确不做）。若将来要变为各自独立，需引入会话隔离。
