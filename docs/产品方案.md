## 1. 为什么推翻 v0.1

v0.1 的模型是「跑批任务」：写 JD → 生成评分卡 → 跑一批 → 出 Excel。它错在四件事：

1. **把持续工作建模成了一次性任务。** 一个岗位在招两周，简历陆续进来。跑批意味着每来一份简历就要重跑一轮、重新打开一次 Excel。而 HR 的真实状态是"一边收简历一边看人"。
2. **步骤多、门槛高。** 要记命令、要管目录结构、要手改 JSON。这些对 HR 来说全是**额外的活**，不是省下来的活。工具的启动成本一旦超过它省下的时间，就没有意义。
3. **结果不在看得见的地方。** Excel 是快照，不是常驻视图。谁被新加了、排名怎么变的，HR 不知道。
4. **批量思维带来错误的默认动作。** 跑批天然要求"先凑齐一批再跑"，而真实场景需要"来一份看一份"。

**结论：判断内核是对的，装错了外壳。** v0.1 里那些关于判断质量的设计（硬门槛用规则、结论带证据、未提及不淘汰、合规红线）全部继承。

## 2. 产品定位

> 把「逐份看简历」变成「看排序结果」。

**产品的基本单位不是"一次筛选任务"，而是"一个在招岗位"。**

每个岗位是一个持续存在的工作台：有 JD、有筛选标准、有不断增长的简历池、有实时更新的优先级排名。HR 打开产品看到的是"我手上这几个岗位现在什么情况"，而不是"我要发起一次筛选"。

---

## 3. 核心用户与场景

- **用户**：一线招聘 HR。同一时间手上 3–10 个在招岗位，每天面对几十到几百份简历。
- **场景**：简历从多渠道陆续投进来。HR 的目标不是"看完所有简历"，而是**不漏掉该看的人、不在明显不合适的人身上花时间**。
- **成功的样子**：HR 打开岗位，只看「推荐」组的前十几份，其余靠排序结果放心跳过。

---

## 4. 设计原则（继承 v0.1，这是不可动的内核）

1. **硬门槛用规则，不用模型。** 学历、年限、专业、地点、跳槽频次是布尔判断——规则成本为 0、准确率 100%、完全可解释。模型只做规则判不了的部分。
2. **每条结论必须带原文引用，并区分「不满足」与「未提及」。** 未提及的项**不得据以淘汰**，标记为「待确认」交人工。引不出原文就承认不知道，禁止编造。
3. **合规红线。** 性别、年龄、婚育、籍贯、民族、健康状况、政治面貌不得进入评分维度。模型会从毕业年份反推年龄，需在判定与输入两侧都显式禁止。
4. **判定口径靠自然语言定义，不靠布尔规则。** 每个维度必须有 `definition` + 正反例。"有 AI 项目经验"真正的难点是口径不清（微调算不算？调 API 算不算？），不是配置。
5. **改标准必须可追溯，且不重跑解析。** 标准有版本号，每次结果记录所用版本；改标准后重排不重新解析简历。

## 5. 功能范围

### 5.1 P0（必须做）

| # | 功能 | 说明 |
|---|---|---|
| 1 | **多岗位并列** | 左栏岗位列表（带简历数），每个岗位独立的标准、简历池、排名 |
| 2 | **新建岗位：提供 JD** | 支持粘贴文本 / 上传文件；自动生成筛选标准草稿供确认 |
| 3 | **简历上传** | 拖拽或选择文件；支持连续添加、多份并发；**上传即处理** |
| 4 | **优先级排名视图** | 三分组（推荐 / 待确认 / 不推荐）；每条一句话理由；展开看证据 |
| 5 | **对话式调整筛选标准** | 用自然语言说，系统给出改动清单 → 确认后生效，并提示对现有排名的影响 |
| 6 | **一键复核** | 列表上直接「同意 / 不同意」，一次点击完成，作为后续校准的唯一输入 |
| 7 | **处理状态可见** | 处理中 / 失败（扫描件等）明确标注，不让 HR 误以为系统已经看过了 |
| 8 | **标准版本化与结果追溯** | 每次排名结果记录所用标准版本，可对比不同标准下的结果 |

### 5.2 P1（可延后）

- 手工粘贴文本兜底（扫描件或解析失败时）
- 导出 Excel（保留为导出功能，**不再是主界面**）
- 同一候选人多岗位/多次投递的识别与合并
- 候选人备注与标签
- 标准改动后的排名变化提示（谁进谁出、为什么）
- 批量操作（批量通过 / 淘汰）

### 5.3 明确不做

自动发拒信、面试安排、题库生成、BI 看板、模型微调、权重自动学习、多人协作与权限模型、向量语义搜索。

## 6. 关键交互约定

### 6.1 上传即处理，但结论"稳定后才呈现"

- 上传后立即进入处理队列，处理完自动进入排名，**不需要 HR 再点任何按钮**。
- 处理中显示「处理中」而**不显示分数**，避免呈现半成品结论。
- 解析失败（如扫描件无文本层）→ 明确标注「需人工」，并给出出路：①手工粘贴文本（P1）②直接从排名中排除。**绝不允许静默跳过**，否则 HR 会误以为系统看过并放过了这个人。

### 6.2 一句话理由的硬约束

- 每条**最多一句话**（建议 30 字内），不允许糊成一段。
- 必须指向**具体标准 + 具体证据**，禁止"综合素质较好"这类无法验证的空话。
- 点开可看到：每条标准的判定结果 + 简历原文引用。

### 6.3 三分组，而不是一条纯排序

| 分组 | 含义 |
|---|---|
| **推荐** | 全部必须项已满足 |
| **待确认** | 有必须项在简历中「未提及」，无法确认是否满足 |
| **不推荐** | 有必须项明确「不满足」 |

**「待确认」必须与「不推荐」分开。** 若合并成一条排序，简历里没写到的人会被当成淘汰，这是最危险的误伤。待确认不是系统的无能，而是交给 HR 的待办清单。

### 6.4 改标准必须确认后生效

- 系统输出：**改了什么** + **对现有排名的影响** + 三个选择（确认生效 / 部分采纳 / 取消）。
- **不允许静默改标准。** HR 授权的是"帮我改"，不是"随便改"。
- 标准每次变更留版本，可回退。

### 6.5 合规红线在自然语言入口同样生效

如果用户说"把 35 岁以上的筛掉"或"已婚未育的先排除"，系统必须**拒绝执行并说明原因**，而不是照做。合规检查不能只加在结构化配置入口上。

---

## 7. 成功标准

1. HR 的工作方式从"逐份看简历"变为"只看推荐组的前 N 份"。
2. **上传到出结果的等待时间**在可接受范围内（目标：单份 ≤ 30 秒，需真实数据实测标定）。
3. HR 对「推荐」组的认可率高（**核心成功标准，需真实批次实测**）。
4. 改标准后立即重排，**不需要重新上传简历**。
5. HR 愿意使用「同意 / 不同意」——这是系统以后变准的唯一输入来源。

## 9. 风险登记

| 风险 | 等级 | 说明与应对 |
|---|---|---|
| **处理速度** | 高 | "上传即处理"的体验完全依赖速度；一旦要等几分钟，产品就会退化成跑批。需并发处理 + 解析缓存（已具备） |
| **一句话理由退化** | 高 | 极易变成套话或幻觉。强制要求指向具体标准与原文证据，无证据不得输出结论 |
| **自然语言改标准被误改** | 中 | 用「改动清单 + 影响提示 + 确认」三道闸，且标准版本可回退 |
| **合规红线从自然语言入口泄漏** | 高 | 输入侧与输出侧都要拦截，不能只在配置侧校验 |
| **解析质量** | 高 | 中文 PDF 版式千变万化，仍是最大技术风险（细节见技术方案） |
| **HR 不信任大量「待确认」** | 中 | 产品上明确定位为"给你的待办清单"。若某必须项长期产生大量待确认，说明该标准的判定口径没写清楚，应引导 HR 修改口径，而不是放宽判定 |

## 10. 未决问题

1. **产品载体形态**：本地桌面应用 / 浏览器网页 / 其他 —— 待技术方案阶段确定。
2. 单机单人使用，还是需要小团队共享同一批岗位数据。
3. 同一候选人投递多个岗位时如何呈现（各自独立，还是关联提示）。
4. "可接受等待时间"的具体阈值，需要真实数据标定。
5. 扫描件兜底是否必须做「手工粘贴文本」，还是先只做「标注需人工 + 排除」。
