## 0. 一次性准备

```bash
cd /d/AI简历初筛

# ① 后端依赖
python -m venv .venv
.venv/Scripts/python.exe -m pip install -r requirements.txt
.venv/Scripts/python.exe -m pip install -e .     # 安装 resume-screen 命令

# ② 前端（只需一次；改了前端代码才需要重跑 build）
cd web && npm install && npm run build && cd ..

# ③ 模型密钥
cp .env.example .env                              # 编辑 .env，填入 DASHSCOPE_API_KEY
```

Windows 下也可以用 `.venv\Scripts\Activate.ps1` 激活，但**本手册一律用完整路径调用**——
激活与否不影响结果，少一个会忘的步骤。

### 先看看界面长什么样（不花钱、不联网）

```bash
.venv/Scripts/python.exe scripts/offline_demo.py --open
```

会自建一个岗位、一份标准，并灌入三份合成简历，让结果**落满三个分组**。
没有这一步，第一次上手看到的是一个空界面，看不出三分组长什么样。

> 不要用 `LLM_PROVIDER=fake` 来"看界面"：它对任何请求都返回空对象，
> 结果是所有字段"未提取"、所有人落进待确认。流程跑通了，但什么都没验证到。

### 环境变量（`.env`）

| 变量 | 说明 | 默认 |
|---|---|---|
| `DASHSCOPE_API_KEY` | 通义千问 API key，**缺失会在启动前明确报错** | — |
| `LLM_PROVIDER` | `qwen` / `fake`（fake 仅供自动化测试） | `qwen` |
| `LLM_MODEL` | 模型名 | `qwen-plus` |
| `DASHSCOPE_BASE_URL` | 自建兼容端点（可选） | DashScope 官方兼容端点 |
| `HOST` / `PORT` | `serve` 的默认监听地址与端口 | `127.0.0.1` / `8000` |
| `APP_DATA_DIR` | 数据目录 | 项目下 `data/` |
| `SCREEN_CONCURRENCY` | 同时处理的简历份数 | `5` |

## 1. 启动

```bash
resume-screen serve
```

```
网页工作台已启动
  打开：http://127.0.0.1:8000/
  停止：在本窗口按 Ctrl+C
```

**从这里开始就不用再碰命令行了。** 需要记命令就说明形态还是错的。

| 参数 | 说明 | 默认 |
|---|---|---|
| `--port` / `-p` | 端口 | `8000` |
| `--lan` | 允许局域网访问，并打印可复制的链接 | 关 |
| `--data-dir` | 数据目录（数据库 + 上传的简历） | `data/` |
| `--concurrency` / `-c` | 同时处理的简历份数 | `5` |

启动前会自动检查并给出可执行的下一步：

- **端口被占用** → 报出占用进程，提示换端口
- **前端未构建** → 提示 `cd web && npm run build`
- **缺 `DASHSCOPE_API_KEY`** → 直接拦住不启动（不会先报"已启动"再甩一堆报错）

### 把链接发给同事（同一局域网）

```bash
resume-screen serve --lan
# 会额外打印：同一局域网的其他电脑可以打开：http://192.168.x.x:8000/
```

对方在浏览器里打开这个地址即可，不需要装任何东西。

> 当前是**单机单人**版本：链接可以共享，但数据只有一份。
> 多人同时改标准会互相覆盖，先约定一个人操作。多人协作在方案里列为明确延后项。

## 2. 建岗位（输入 JD）

左栏「新建岗位」→ 填岗位名称 + 把 JD 粘进去。

- **一个岗位 = 一个工作台**：自己的 JD、自己的筛选标准、自己的简历池和排名。
- 要同时筛多个岗位就建多个岗位，左栏点着切换，互不干扰。
- 岗位可以归档：归档后不再出现在列表里，已有的简历和结论保留。

JD 决定这一轮的口径，写得越具体，后面生成的标准越贴。JD 之后也可以改。

---

## 3. 生成筛选标准（**最关键的一步**）

新建岗位后会自动弹出标准抽屉。

1. 点「**由 JD 生成草稿**」，系统给出必须项 / 加分项 / 减分项。
2. 看每个维度的 `definition`（判定口径）和正反例，**不对就在 JSON 里直接改**。
3. 点「**保存并按新标准重排**」才生效。

### 为什么草稿一定要人工过一遍

「有 AI 项目经验」这类条件的真正难点不是配置，是**口径**：

- 调过一次接口算不算？
- 跟着别人做的项目算不算？
- 课程作业里的模型微调算不算？

口径不写清楚，同一份简历每次判定都可能不同，用起来会以为"这个模型不稳定"。
`positive_examples` 写"独立微调过模型、搭建过 RAG 流程"，
`negative_examples` 写"仅调用接口写周报"——边界就明确了。

### 能规则化的条件务必标上 `rule`

规则判定准确率 100%、零调用成本、完全可解释，而模型不保证。内置规则：

| rule id | 用途 | params 示例 |
|---|---|---|
| `min_degree` | 学历门槛 | `{"min_level": "本科"}` |
| `min_years` | 工作年限门槛 | `{"min_years": 3}` |
| `major` | 专业对口 | 见内置示例 |
| `location` | 工作地点 | 见内置示例 |
| `job_hop` | 跳槽频次 | `{"min_avg_months": 12}` |

### 合规红线

性别、年龄、婚育、籍贯、民族、健康状况、政治面貌**不能进入评分维度**。
生成草稿时系统会自动剔除这类维度并列出来；用自然语言提要求时会被当场拒绝。

模型会从毕业年份反推年龄，所以年龄类的迂回表达也在拦截范围内。

## 4. 上传简历

把 PDF 拖到上传区，或点击选择文件。

- 支持一次多份、**连续追加**。来一份传一份。
- **上传即处理**，没有"开始筛选"按钮——不需要凑齐一批，也不需要再确认一次。
- 处理中会显示状态（排队中 / 解析中 / 提取中 / 评估中）。
  **处理中不显示分数**，免得拿半成品下判断。
- 同一份文件（按内容哈希判断）重复上传只会合并为一条，不会重复评估、不会重复计费。

### 解析不出来怎么办（扫描件 / 图片型 PDF）

有一类 PDF 看起来是简历，其实**正文是一张图片**，没有可提取的文字。它有两种长相：

| 长相 | 系统看到什么 |
|---|---|
| 扫描件 | 一个字都没有 |
| 招聘平台导出的图片型 PDF | **只有一串重复的水印文字**（同一串字符重复十几次），正文全在图里 |

两种都会让系统：

- 把状态标为「**需人工**」，并在面板里写明原因（例如"页面主体为图片（占版面 100%），
  文本层去除重复后仅 50 字…"）；
- **不出现在排名里**，也不会被静默跳过。

> 为什么要专门处理第二种：水印那串字把"文本够不够长"这个判据骗过去了，
> 系统一度会认为"这份能读"，于是把它送进模型。模型对着水印只能编字段，
> 界面上却显示"处理成功"——看起来正常，实际全是编造。**这类错误比报错危险得多**，
> 所以判据已改为看"去掉重复后还剩多少字"和"这一页有多少面积是图片"。

出路在上传区下方：「**扫描件识别不出来？粘贴简历文本**」。把简历正文粘进去，
它走完整的评估链路，和其他简历一起排序。

> 不做 OCR 是刻意的选择：粘进来的是你亲自确认过的内容，
> 不存在"OCR 认错了还查不出来"的风险。

## 5. 看排名（三组，不是一条排序）

结果分三组，**这个区分是这套东西最不能省的地方**：

| 分组 | 含义 | 你该做什么 |
|---|---|---|
| **推荐** | 所有必须项都满足 | 直接往下走流程 |
| **待确认** | 有必须项**简历里没写**，或内容无法判定 | 去确认这一项，**这不是淘汰** |
| **不推荐** | 有必须项**明确不满足** | 可以放心筛掉，理由带原文依据 |

**"未提及"不等于"不满足"**。简历没写学历的人，和学历明确不够的人，是两回事——
前者可能是漏写了，后者是硬性不符。混在一起会误伤候选人。

每条结论都能展开，看到：

- 每个维度的判定（满足 / 不满足 / 未提及 / 无法判定）
- 判定者是谁（**规则**还是模型）——规则判的可以完全信任，模型判的需要你留意口径
- **原文引用**（第几页、原话是什么）。引不出原文就写"无原文引用"，不编造。

每行右侧有「同意 / 不同意」记录你的复核判断，导出 Excel 时会带上——
这样表发给业务方时，他们看到的是"HR 已经看过并同意"的结论，而不是模型自说自话。

## 6. 用一句话改标准

工作区顶部就是输入框，直接写你想怎么改：

```
把 AI 项目经验改成必须项
学历不卡了
加大厂经历的权重，从 20 提到 45
再加一条：有招聘系统搭建经验
```

系统会分三步走，**不会直接改掉**：

1. **给改动清单**：删了哪个维度、改了什么、为什么。默认全选，你可以取消其中几条。
2. **给影响预估**：会动到谁 ——「推荐 1 → 3、待确认 1 → 0、不推荐 1 → 0」，
   并列出具体是哪几份简历会换组。
   - 涉及**新增维度或口径变化**时，系统会明说"**无法精确预估**"，并**不显示改动后的数字**。
     这类改动没法从旧结论推算，宁可说算不准，也不给一个会被当真的假数字。
   - 还有几份简历没出结论（处理中 / 需人工）也会单独提示，避免你以为预估覆盖了全部。
3. **等你确认**：可以「全部采纳」、「只采纳选中的 N 项」、或「取消」。

生效后标准记为新版本，排名按新标准重排——**只重跑评分，不重新解析简历**，
所以改完立刻能看到新排名。

### 会被拒绝的说法

```
把 35 岁以上的筛掉        → 拒绝：涉及年龄
已婚未育的先排除          → 拒绝：涉及婚育
只要男生                  → 拒绝：涉及性别
不要某省的                → 拒绝：涉及籍贯
```

拒绝时会给理由，并给一条出路：**说清你真正想筛的能力或经验，让系统把它翻成可判定的口径**。
这类请求**不会产生模型调用**（拦截发生在调用之前），也不会改变任何标准。

被拒绝的请求同样会存档——"我提过这个要求、被拒了、理由是什么"在复盘时有用。

## 7. 标准版本与回滚

每次改标准都留一个新版本，旧版本不删。标准抽屉底部能看到全部历史版本。

- 当前版本会标出来，不能回滚到自己。
- 「**回滚到此版本**」= 把旧版本重新设为当前版本，并立刻按它重排。
- 回滚**不删历史**："改了又改回来"这件事本身也留在版本记录里，复盘时看得到。
- 提案（谁在什么标准基础上提了什么要求）也存档，标准可追溯不只看版本号。

## 8. 导出 Excel

右上角「**导出 Excel**」。

- 顺序**与屏幕一致**（推荐 → 待确认 → 不推荐）
- 带上你的复核判定，拿来就能发业务方，不需要再人工对一遍
- 每行带结论与原文证据

未设标准时导出会被拦下并说明原因，不会给你一张没有结论的空表。

## 排错速查

| 现象 | 原因与处理 |
|---|---|
| 启动报缺 `DASHSCOPE_API_KEY` | 复制 `.env.example` 为 `.env` 并填入 key；只想看界面用 `scripts/offline_demo.py` |
| 启动提示端口被占用 | 换端口：`resume-screen serve -p 8011`；提示里会给出占用进程 |
| 打开是空白页 / 顶栏没样式 | 前端没构建：`cd web && npm run build` |
| 简历一直"处理中" | 看该行状态。解析失败会明确标"需人工"或"失败"，不会静默卡住 |
| 简历标「需人工」 | 正文是图片（扫描件，或"整页图片 + 只有水印"的平台导出件）。用上传区下方的「粘贴简历文本」兜底 |
| 大量「待确认」 | 正常。简历未提及的必须项不会据以淘汰，交人工核实 |
| 「必须项 0 · 加分项 0」 | 标准没生成出来（常见原因是 key 无效）。程序会明确提示，不会静默产出空标准 |
| 改了标准排名没变 | 确认点了「保存并按新标准重排」或「确认生效」；只改草稿不生效 |
| 上传多份只进来一份 | 内容完全相同（按内容哈希判断），已合并为同一条并在界面提示 |
| 想让同事打开链接 | 用 `resume-screen serve --lan`，把打印出的局域网地址发过去 |
| 一行里写「无原文引用」 | 该结论在简历里找不到对应原文。这是"承认不知道"，不是故障 |

| 路径 | 类型 | 是否入库 |
|---|---|---|
| `data/` | 运行时数据：SQLite 库 + 上传的简历 + 缓存 | 否 |

已通过 `.gitignore` 排除，提交前仍建议 `git status` 自查。

## 开发相关

```bash
.venv/Scripts/python.exe -m pytest -q                     # 206 passed
cd web && npm run typecheck && npm run build              # 前端类型检查 + 构建
```

分层约定（改动前必读）：

```
cli/ 薄壳 → web/ 只做入参校验与调用 → services/ 业务编排 → core/ 纯逻辑 → store/ SQLite
                                          adapters/{parsers, llm, exporters} 可插拔
```

- `core/` **不认识 FastAPI、不认识 CLI、不依赖具体 SDK**。业务逻辑写进 web 层，后期抽不出来。
- **新增能力 = 加适配器，不动核心。** 加 docx 解析 = 注册一个 parser；换模型 = 改 base_url/model。
- 每次改动必须建对应 Git commit，并编写/更新测试且全部通过——见 `AGENT.md`。

### 两道验证防线

1. **接口契约测试**（`tests/test_m7_ui_contract.py`）：前端声明的接口后端必须存在；
   **后端实现了的 P0 动作界面上必须有入口**（反向那条是最难发现的缺口）。
2. **真浏览器冒烟**（`web/e2e/ui-smoke.mjs`，配 `scripts/offline_demo.py`）：
   HTTP 测试全绿不代表界面能看。M7 就踩过一次——接口 200、响应 20ms，但页面白屏。

```bash
.venv/Scripts/python.exe scripts/offline_demo.py --smoke --chat "学历不卡了"
```
