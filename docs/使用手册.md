## 0. 一次性准备

```bash
cd /d/AI简历初筛
source .venv/Scripts/activate      # 激活后命令是 resume-screen
cp .env.example .env               # 编辑 .env，填入 DASHSCOPE_API_KEY
```

确认可用：`resume-screen version` 输出版本号即正常。

> Windows PowerShell 用 `.venv\Scripts\Activate.ps1`；Git Bash 用 `source .venv/Scripts/activate`。

### 环境变量（`.env`）

| 变量 | 说明 | 默认 |
|---|---|---|
| `DASHSCOPE_API_KEY` | 通义千问 API key，**缺失会明确报错** | — |
| `LLM_PROVIDER` | `qwen` / `fake`（fake 仅供离线演练） | `qwen` |
| `LLM_MODEL` | 模型名 | `qwen-plus` |
| `DASHSCOPE_BASE_URL` | 自建兼容端点（可选） | DashScope 官方兼容端点 |

## 1. 放简历

把简历 PDF 放进 `resumes/`。

- 只扫描该目录**顶层**，子文件夹不会被递归
- 只处理 `.pdf`，其他格式会被**静默跳过**（不报错，注意核对数量）
- 文件名随意，中文名也可以；系统按**文件内容哈希**生成 ID，改名不影响缓存

## 2. 写 JD

存为纯文本文件，例如 `jd/ai.txt`。命令行也可以直接用 `--jd "文本"` 传入，但长 JD 建议用文件，便于修改与复用。

## 3. 生成评分卡草稿

```bash
resume-screen rubric new \
  --jd-file jd/ai.txt \
  --out rubrics/ai.json \
  --version 2026-09-26-ai-must \
  --job-title "AI应用开发工程师"
```

输出会显示「必须项 N / 加分项 N / 减分项 N」。

**确认点**：如果 N 为 0，说明没有生成出来——先检查 `.env` 的 key 是否配置正确。程序对此会给出明确提示，不会静默产出空评分卡。

## 4. 人工编辑评分卡（最关键的一步）

打开 `rubrics/ai.json`，对每个维度做两件事。

### ① 能规则化的，写进 `rule` 字段

规则判定准确率 100%、零调用成本、完全可解释。现有内置规则：

| rule id | 用途 | params 示例 |
|---|---|---|
| `min_degree` | 学历门槛 | `{"min_level": "本科"}` |
| `min_years` | 工作年限门槛 | `{"min_years": 3}` |
| `major` | 专业对口 | 见示例文件 |
| `location` | 工作地点 | 见示例文件 |
| `job_hop` | 跳槽频次 | `{"min_avg_months": 12}` |

### ② 规则判不了的，`rule` 留 `null` 走 LLM

例如"有 AI 项目经验"。这类维度**必须**把 `definition` + `positive_examples` + `negative_examples` 写清楚——"调 API 算不算""课程项目算不算"这类边界不写清楚，模型每次判定结果都可能不同，容易被误认为模型不稳定。

权重调整：`bonus[].weight`（加分）、`red_flags[].penalty`（扣分）。

示例见 `rubrics/example.json`。

## 5. 校验评分卡

```bash
resume-screen rubric validate rubrics/ai.json
resume-screen rubric show rubrics/ai.json
```

`validate` 会检查合规红线（性别、年龄、婚育、籍贯、民族、健康状况、政治面貌不得进入评分维度）、口径完整性、版本号，并提示哪些硬门槛未走规则。

## 6. 小批量试跑

```bash
resume-screen screen --rubric rubrics/ai.json --input resumes/ \
  --limit 5 --out data/output/试跑.xlsx
```

**确认点**：先看这 5 份的结论与原文证据是否符合预期。口径不对就回到第 4 步修改，确认无误再全量跑。

## 7. 全量筛选

```bash
resume-screen screen --rubric rubrics/ai.json --input resumes/ \
  --out data/output/初筛结果.xlsx --cache-dir data/cache --run-dir data/runs
```

输出摘要中包含 **run_id**，第 8 步要用。

Excel 内容：排名 / 姓名 / 联系方式 / 判定（通过·待确认·淘汰）/ 得分 / 命中维度 / 结论与原文证据 / 原文件路径。"待确认"行标黄。

| 参数 | 说明 |
|---|---|
| `--limit N` | 只处理前 N 份，调试用 |
| `--no-cache` | 忽略缓存，强制重新解析与提取 |
| `--model qwen-max` | 换模型 |
| `--provider fake` | 离线演练，不联网不消耗 token |

## 8. HR 复核回写

HR 在 Excel 的「HR复核判定」列选择判定值并保存，然后：

```bash
resume-screen review --excel data/output/初筛结果.xlsx \
  --run data/runs/<run_id>/run.json
```

回写结果存为 `data/runs/<run_id>/review.json`，**这是后续校准权重的唯一依据，不要删除**。

## 业务口径变化时（高频场景）

```bash
cp rubrics/ai.json rubrics/ai-v2.json   # 只改这个 JSON
resume-screen screen --rubric rubrics/ai-v2.json --input resumes/
```

- 不需要动简历，也不会重新解析（解析结果按文件内容哈希缓存，换侧重几乎不再产生解析成本）
- 两次运行各自记录 `rubric_version`，可直接做 A/B 对比，不会混在一起

## 排错速查

| 现象 | 原因与处理 |
|---|---|
| 「筛选完成：0 份简历」 | 简历不在 `resumes/` 顶层，或不是 `.pdf` |
| `MissingAPIKeyError` | `.env` 未配 key；离线演练请加 `--provider fake` 或设 `LLM_PROVIDER=fake` |
| 判定结果大量「待确认」 | 正常。简历未提及的项不会据以淘汰，交人工核实 |
| 某行标「需人工处理」 | 扫描件/图片型 PDF 无文本层，按设计不送入模型 |
| 改了评分卡但结果没变 | 确认 `--out` 指向新文件；必要时加 `--no-cache` |
| 数量比预期少 | 目录里混入了非 PDF 文件，会被静默跳过 |

## 目录速查

| 路径 | 类型 | 是否入库 |
|---|---|---|
| `jd/` | 岗位 JD（输入） | 否（内部业务资料） |
| `resumes/` | 简历（输入） | 否（含个人信息） |
| `rubrics/` | 评分卡（JD 的输出、筛选的输入） | 是 |
| `data/output/` | Excel 结果 | 否 |
| `data/cache/` | 解析与提取缓存 | 否 |
| `data/runs/<run_id>/` | 运行存档 + HR 回写 | 否 |
| `fixtures/` | 真实脱敏样本（本地留存） | 否 |

**安全约定**：真实简历、JD、导出结果一律不得提交进 Git。已通过 `.gitignore` 排除，提交前仍建议 `git status` 自查。
