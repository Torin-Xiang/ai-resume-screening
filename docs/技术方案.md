## 1. 目标与非目标

### 1.1 本阶段要达成的

在**本机**跑起一个浏览器应用，验证产品构想成立：能建多个岗位、上传简历后自动处理、排名常驻并实时更新、能用一句话改筛选标准。

### 1.2 本阶段明确不做

- 公网部署、域名、HTTPS（架构预留，实现不做，见 §3）
- 账号、登录、权限
- 多人协作下的数据隔离
- 性能压测与大规模批处理（但在 §10 给出实测要求）

### 1.3 判断标准

以产品方案 §7 为准。技术上只补一条：**"分享"能力不能因为实现方式而被写死**——将来加部署时，不允许出现"必须改代码才能部署"的情况。

## 2. 关键决策

### 2.1 载体：FastAPI 后端 + React 前端

**决策**：后端用 FastAPI（Python），前端用 Vite + React + TypeScript。

**理由**：

1. **判断内核是 Python 且已完成**（101 项测试通过）。后端换语言等于把最贵的资产丢掉重写，没有讨论余地。
2. **不用 Streamlit / Gradio**。这类工具的执行模型是"每次交互从头重跑整个脚本"，而本产品的三个核心交互恰好都撞在这个模型上：
   - 上传后要在**后台持续处理**，不能因为用户点了别处就中断；
   - 处理状态要**局部实时更新**（SSE），而不是整页重刷；
   - 排名是**常驻视图**，会话状态丢失就意味着用户要重做一遍。
   用它们能很快做出 demo，但会在最关键的体验上返工。
3. **前端用 React 而不用手写原生 JS**：交互复杂度足够高（多文件上传队列、逐份处理状态、三分组排名、详情展开、对话面板），手写状态管理到这个量级会失控，而这是要长期迭代的产品。

**代价**：引入第二套语言与构建步骤（Node）。可接受——构建产物是静态文件，运行时仍只有一个 Python 进程。

### 2.2 "复制链接就能用"的真相

这一条必须写在方案里，因为它极易被误解，且直接决定架构。

**在自己电脑上跑的服务，地址是 `http://127.0.0.1:8000`，只有本机能打开。** 把链接发给别人，对方打不开——这不是网页形态自带的能力，而是部署方式决定的。

| 档位 | 做法 | 谁能访问 | 前置条件 | 本阶段 |
|---|---|---|---|---|
| ① 本机 | 绑 `127.0.0.1` | 只有自己 | 无 | **做** |
| ② 局域网 | 绑 `0.0.0.0` | 同一网络的同事 | 防火墙放行、知道本机 IP | 留能力，不启用 |
| ③ 公网 | 部署到服务器 | 任何拿到链接的人 | 一台服务器、数据持久化 | 不做 |

**架构上为 ③ 预留的具体要求**（不全做，但设计时不能堵死）：

- 前端与后端彻底分离，前端是静态文件，可独立托管；
- 监听地址与端口从环境变量读取（`HOST` / `PORT`），不写死在代码里；
- 上传的原始文件与数据库落在**可配置的数据目录**（`APP_DATA_DIR`），不散落在项目里，否则搬机器要手工找文件；
- **API key 只在服务端**，前端永远不接触，也不通过网络下发——这也是"使用者打开链接就能用、不需要配 key"的前提（见产品方案 §9 风险「无法自行运行」）。

### 2.3 存储：SQLite

**决策**：用 SQLite（Python 标准库 `sqlite3`），不用 JSON 文件，也不用 PostgreSQL。

**理由**：

- 产品的四类实体（岗位 / 简历 / 标准版本 / 结果）之间是明确的关联关系，且需要频繁读取"某岗位当前排名"，JSON 文件每次都要全量扫描并自行维护引用一致性。
- SQLite 零依赖、单文件，**备份和搬机器就是复制一个文件**——对"先本机跑、将来可能换服务器"的路径最友好。
- 单人使用下没有并发写压力，不需要引入 PostgreSQL 与相应的运维成本。将来真要多人用，SQL 层几乎可以平移。

**代价**：失去 v0.1"结果就是一堆可读 JSON"的直观性。应对：提供导出命令，且关键表保留 `payload` 列存完整 JSON，必要时可直接查看。

### 2.4 处理队列：进程内异步队列 + 并发限流

**决策**：应用内起一个后台 worker（`asyncio` 任务 + 队列），不引入 Celery / Redis。

**理由**：

- 单机单人，引入外部消息中间件只增加运维面，不解决任何当期问题。
- 瓶颈是 LLM 的网络等待（IO 密集），不是 CPU，`asyncio` 足够。
- 但**必须做并发限流**：并发数从环境变量配置（默认 5），避免触发服务商限流；同时保证**并发不改变结果**——同一批简历无论并发几路，结论必须一致（这是产品方案 §7「稳定性」的硬要求，评分层必须是无状态纯函数，已有的 `evaluate_candidate` 满足）。

**代价 / 已知技术债**：进程重启会丢失进行中的任务。应对：任务状态落库，重启后把 `pending/processing` 的任务重新入队（状态机里必须有这一条，否则简历会永久卡在"处理中"）。

**为什么现在不做队列抽象**：接口按"入队 / 查询状态"设计即可，将来换 Celery 只改这一个模块。

### 2.5 数据目录与密钥

```
APP_DATA_DIR/            # 默认 <项目根>/data，可由环境变量覆盖
├── app.db               # SQLite
├── uploads/             # 上传的原始 PDF（按 resume_id 命名，天然去重）
└── cache/               # 解析缓存（沿用 v0.1 的 ResumeCache）
```

`.env`（已在 `.gitignore` 中）承载 `DASHSCOPE_API_KEY`、`LLM_PROVIDER`、`APP_DATA_DIR`、`HOST`、`PORT`、并发数等。

3. LLM 调用仍只走 `core/llm.py` 的统一入口（重试 / 限流 / 成本计量），禁止在 service 里裸调 SDK。

## 4. 数据模型

### 4.1 表设计

```sql
-- 岗位：产品的基本单位
CREATE TABLE jobs (
  job_id      TEXT PRIMARY KEY,
  title       TEXT NOT NULL,
  jd_text     TEXT NOT NULL DEFAULT '',
  status      TEXT NOT NULL DEFAULT 'open',      -- open / archived
  created_at  TEXT NOT NULL,
  updated_at  TEXT NOT NULL
);

-- 标准版本：每次改动留一版，可回退、可对比（产品方案 §6.4）
CREATE TABLE rubric_versions (
  rubric_id   TEXT PRIMARY KEY,
  job_id      TEXT NOT NULL REFERENCES jobs(job_id),
  version     TEXT NOT NULL,
  payload     TEXT NOT NULL,                      -- 完整 Rubric JSON
  note        TEXT NOT NULL DEFAULT '',           -- 本次改动的来源与原因
  created_at  TEXT NOT NULL
);

-- 解析结果缓存：与岗位无关，同一文件内容全局共享
CREATE TABLE resume_docs (
  resume_id   TEXT PRIMARY KEY,                   -- 文件内容 hash
  doc_payload TEXT NOT NULL,                      -- ResumeDocument
  parse_status TEXT NOT NULL,
  created_at  TEXT NOT NULL
);

-- 简历与岗位的关联 + 处理状态
CREATE TABLE job_resumes (
  job_id      TEXT NOT NULL REFERENCES jobs(job_id),
  resume_id   TEXT NOT NULL,
  file_name   TEXT NOT NULL,
  stored_path TEXT NOT NULL,
  origin      TEXT NOT NULL DEFAULT 'upload',     -- upload / paste
  status      TEXT NOT NULL,                      -- queued/parsing/extracting/scoring/done/needs_manual/failed
  error       TEXT NOT NULL DEFAULT '',
  created_at  TEXT NOT NULL,
  updated_at  TEXT NOT NULL,
  PRIMARY KEY (job_id, resume_id)
);

-- 结论：同一份简历在不同标准下的结果各自保存，便于 A/B 对比
CREATE TABLE results (
  job_id      TEXT NOT NULL,
  resume_id   TEXT NOT NULL,
  rubric_id   TEXT NOT NULL,
  verdict     TEXT NOT NULL,                      -- recommend / needs_review / not_recommend
  score       REAL NOT NULL DEFAULT 0,
  reason_line TEXT NOT NULL DEFAULT '',           -- 一句话理由（≤30 字）
  payload     TEXT NOT NULL,                      -- 完整 CandidateResult
  hr_decision TEXT,                               -- 一键复核回写
  updated_at  TEXT NOT NULL,
  PRIMARY KEY (job_id, resume_id, rubric_id)
);
```

**关键设计说明**：

1. **`resume_docs` 与 `jobs` 解耦**，是"改标准不重跑解析"的实现基础。解析与提取只依赖文件内容，所以缓存可以直接全局复用；改标准只重算 `results`。
2. **`results` 的主键含 `rubric_id`**，所以换标准重排是"新增一批结果"而非"覆盖旧结果"，A/B 对比天然成立。
3. **`status` 是显式状态机**，不用布尔标记。这样"处理中不显示分数"（产品方案 §6.1）在数据层就能保证——前端只渲染 `done` 的记录。

### 4.2 状态机

```
queued → parsing → extracting → scoring → done
   ↓        ↓          ↓           ↓
 needs_manual（无文本层，不送模型）  failed（解析或调用异常）
```

- `needs_manual` 与原 `ParseStatus.NEEDS_MANUAL` 对应，**绝不等同于失败或淘汰**，界面上给出口：粘贴文本。
- 应用启动时，把仍处于 `queued/parsing/extracting/scoring` 的记录重置为 `queued` 并重新入队（对应 §2.4 的技术债应对）。

## 5. 接口设计

### 5.1 REST

```
GET    /api/jobs                                岗位列表（含简历数与待确认数）
POST   /api/jobs                                新建岗位（title + jd_text）
GET    /api/jobs/{job_id}                       岗位详情（含 JD、当前标准）
PATCH  /api/jobs/{job_id}                       改标题 / 归档

GET    /api/jobs/{job_id}/rubric                当前标准
PUT    /api/jobs/{job_id}/rubric                直接编辑标准（结构化表单）
GET    /api/jobs/{job_id}/rubric/versions       版本列表
POST   /api/jobs/{job_id}/rubric/rollback       回滚到指定版本

POST   /api/jobs/{job_id}/resumes               上传（multipart，多文件）
POST   /api/jobs/{job_id}/resumes/text          粘贴文本兜底
GET    /api/jobs/{job_id}/resumes               简历列表与处理状态
DELETE /api/jobs/{job_id}/resumes/{resume_id}   移除

GET    /api/jobs/{job_id}/ranking               三分组排名
POST   /api/jobs/{job_id}/ranking/rebuild       按当前标准重排（不重新解析）

POST   /api/jobs/{job_id}/rubric/propose        自然语言改标准 → 变更提案
POST   /api/jobs/{job_id}/rubric/apply          确认应用提案

POST   /api/jobs/{job_id}/review                一键复核（同意 / 不同意）
GET    /api/jobs/{job_id}/export                导出 Excel

GET    /api/jobs/{job_id}/events                SSE 事件流
```

### 5.2 SSE 事件

```
event: resume.status     { resume_id, status, error? }
event: ranking.updated   { job_id, counts: { recommend, needs_review, not_recommend } }
event: job.updated       { job_id }
```

**为什么用 SSE 而不是 WebSocket**：数据流是单向的（服务端 → 浏览器），SSE 基于普通 HTTP、自动重连、实现和调试都更简单，且后端不需要维护双向连接状态。

**推送策略**：单份完成后推 `resume.status`；排名变更做短窗口合并（200ms）后推一次 `ranking.updated`，避免批量上传时刷屏。

## 6. 上传到排名出现的完整链路

```
① 浏览器 POST 多文件
② 服务端按内容 hash 存盘（同名内容天然去重）→ 写 job_resumes(status=queued) → 立即返回 202
   （不在这里做解析，避免请求超时；用户看到的是"已收到，处理中"）
③ 后台 worker 取任务：
     parsing      → 调用 parser 解析 PDF，质量自检
     （needs_manual → 推事件，结束；不送模型）
     extracting   → 查 resume_docs 缓存；命中则跳过模型调用
     scoring      → evaluate_candidate(doc, rubric)
④ 写 results，job_resumes.status=done
⑤ 推 SSE：resume.status → 前端更新该行；排名合并窗口到点后推 ranking.updated
⑥ 前端重排三分组，HR 看到新人出现在正确的位置
```

**这里最关键的一点**：②③分离是"上传即处理"能成立的前提。如果上传请求里同步处理，一份 15 秒、十份就超时，用户看到转圈然后失败——正好退化成产品方案里最担心的那种体验。

## 7. 对话式改标准的实现

这是 v1.0 相对 v0.1 唯一**全新**的判断层，需要单独说明。

**不做的事**：让模型直接输出一份新的标准 JSON。那样无法向用户解释改了什么，也无法计算影响。

**做法**（三段式，对应产品方案 §6.4 的三道闸）：

```
① 生成提案
   输入：当前标准 JSON + 用户那句话 + 岗位 JD
   输出：结构化的变更清单
   [ {op: "add"|"remove"|"modify", 目标维度, 改前, 改后, 理由} , ... ]
   约束：不得输出清单之外的内容；涉及合规敏感项（性别/年龄/婚育等）直接拒绝

② 计算影响（纯计算，不调用模型）
   对已缓存的 ResumeDocument 用"新标准"重算一遍 → 与新标准生效前的分组对比
   输出：谁从推荐掉到不推荐、谁从待确认升上来、各分组数量变化

③ 确认生效
   用户看清单 + 影响，选"确认 / 部分采纳 / 取消"
   确认后：写 rubric_versions 新版本（note 记录来源原话）→ 重排 → 推事件
```

**为什么影响计算不调模型**：评分层已经是纯函数，换标准重算不需要重新解析也不需要重新提取，成本近乎为零。这也是"改标准后立即重排"（产品方案 §7 门槛标准）能成立的原因。

**合规拦截位置**：在 ① 的输入侧（用户原话）和 ① 的输出侧（模型给出的清单）**各拦一次**。只在其中一侧拦都不够：输入侧过滤不了模型的自由发挥，输出侧过滤不了用户的迂回表达。

```

│ 岗位列表     │  岗位标题 · JD 摘要 · 当前标准 v3（改标准入口）│
│              ├────────────────────────────────────────────┤
│ AI 应用开发  │  上传区：拖拽 PDF / 选择文件 / 粘贴文本       │
│  · 42 份     ├────────────────────────────────────────────┤
│              │  排名视图（三分组）                           │
│ 招聘专员     │   推荐      12 份  ← 一句话理由 + 展开证据     │
│  · 18 份     │   待确认     5 份  ← 标注缺哪一项             │
│              │   不推荐    25 份  ← 明确不满足哪一项          │
│ + 新建岗位   ├────────────────────────────────────────────┤
│              │  对话输入：用一句话改筛选标准                 │
└──────────────┴────────────────────────────────────────────┘
```

**三个必须落到界面上的约定**（来自产品方案 §6）：

1. **处理中显示"处理中"而不显示分数**，同一行的状态变化靠 SSE 就地刷新，不重排整页。
2. **"待确认"与"不推荐"视觉上分组且配色不同**，并明确写出缺的是哪一项——这是"未提及不得淘汰"在界面上的落地。
3. **改标准必须弹确认卡**（改动清单 + 影响 + 三个按钮），不允许一句话直接生效。

## 10. 性能要求与实测点

> **状态：全部未实测（阻塞在 M8）。** 缺 `DASHSCOPE_API_KEY` 与真实脱敏简历样本，
> 下表的数字目前一个都没有。已经拿到的是**存储层**的数字（不再是瓶颈）：
> 单次读连接 4.1ms、单次写事务 8.2ms（此前分别是 WAL 75ms / DELETE 76ms，
> 见 `store/db.py` 的两张对照表）。剩下的耗时主要来自模型调用，必须等真实 key 才知道。
> "等待时间超出忍耐"是本方案自己标注的最高风险，**这件事没有数字就等于没有结论**。

| 指标 | 目标 | 实测方式 |
|---|---|---|
| 单份简历端到端 | ≤ 30 秒 | 真实 PDF 计时，含 2 次模型调用 |
| 10 份并发上传 | ≤ 60 秒 | 默认 5 路并发下计时 |
| 换标准重排 | ≤ 3 秒 | 不调模型，纯重算 |
| 首屏可交互 | ≤ 2 秒 | 本地 |

**并发数的确定方式**：不要拍脑袋定。用真实 API 做阶梯测试（2 / 5 / 8 路），记录"总耗时 + 是否触发限流"，取不触发限流的最快档。此前 `tenacity` 的重试会掩盖限流，所以测试时要记录重试次数。

**性能不达标时的取舍顺序**：先加并发 → 再查缓存命中率（同批不加 `--no-cache`）→ 再看是否合并提取与评估的两次调用 → 最后才考虑换模型。**不允许**为了速度砍掉证据机制或合规检查。

### 11.1 界面怎么验（M7 起）

HTTP 测试全绿不等于界面能看。M7 踩到的问题全部只有真浏览器才暴露：

| 现象 | 真实原因 |
|---|---|
| 整页白屏 | Windows 注册表把 `.js` 映射成 `text/plain`，浏览器拒绝执行模块脚本 |
| 右栏显示"还没有可看的排名" | 三个请求共用 `Promise.all` + 吞错，任一失败则整屏看起来"没有数据" |
| 截图里是空界面 | 截图时机早于数据到达，去查了一个不存在的 bug |

因此留两个入口，各自负责不同的事：

- **`tests/test_m7_ui_contract.py`（自动化，进测试套件）**——两个方向的漂移都拦住：
  ① 前端声明的每个接口后端必须存在；② **后端实现了的 P0 动作，界面上必须真的有入口**。
  前者在 TypeScript 编译期查不出来（前端改路径、后端重命名，两边都能编译通过）；
  后者更隐蔽——功能"存在"但用户碰不到，测试全绿也说明不了什么。
  外加 `index.html` 引用的资源都在、MIME 正确。
- **`web/e2e/ui-smoke.mjs`（需要真浏览器）**——自己拉起 Chrome，**轮询到候选人真正渲染出来再截图**，
  可用 `EXPECT_ROWS` 当断言用。M9/M10 起它还能**驱动界面**（`CHAT` / `APPLY` / `EXPECT_REFUSED` /
  `EXPORT`）：把"一句话改标准"这条链路真点一遍。这条链路跨三个请求和一次人的确认，
  只靠接口测试验不到"点得到、点完真的重排了"。

配套的 `scripts/offline_demo.py` 提供**确定性的数据**：不联网、不需要 key，
合成三份必然落满三个分组的简历（必须项满足+命中加分项 / 简历没写学历 / 学历明确不满足）。
没有它，验收就得先申请 key 再准备脱敏简历，门槛高到没人会天天跑。

```bash
# 一条命令：起服务 → 灌数据 → 开真浏览器 → 走完改标准 → 退出
.venv/Scripts/python.exe scripts/offline_demo.py --smoke --chat "学历不卡了"
```

**启动入口的坑（也已修）**：缺 `DASHSCOPE_API_KEY` 时服务其实**起不来**（`QwenClient` 构造即抛错），但最早的实现会先打印"网页工作台已启动"、紧接着甩一个库的 Traceback——两句话自相矛盾。现在 `serve` 在启动前就检查并给出两条出路（配 `.env` 或离线演示脚本），端口占用同理。启动命令是用户碰到的第一道门，它不说人话，前面做得再好也白搭。

**M6/M7/M9/M10 验收结果（脚本化模型 + 真实 Chrome）**：走完「建岗位 → 生成标准草稿 → 上传 3 份 PDF → 三分组排名」，
三份分别落在**推荐 / 待确认 / 不推荐**（待确认那份的理由是「「本科及以上」简历未提及，待确认」，
不推荐那份是「「本科及以上」不满足：大专」——**未提及与不满足分到两组**，这是最不能省的一条）；
展开可见维度判定、判定者（规则 / 模型）与原文引用。随后在同一个页面里输入"学历不卡了"，
看到清单「删除 必须项「本科及以上」」与影响预估「推荐 1→3、待确认 1→0、不推荐 1→0」，
确认生效后标准变 `v1-2`、三份全部升到推荐。另测"把 35 岁以上的候选人筛掉"被当场拒绝且不产生模型调用。

用脚本化模型验收是有意的：**把交互链路问题与模型质量问题分开**。链路是确定性的、现在就能判定；
模型准不准必须等 M8 拿真实简历看，混在一起验会互相掩盖。

### 11.2 这一轮靠验收发现的、测试没发现的问题

留下记录是因为它们说明了一件事：**"测试全绿"与"能用"之间隔着一层，那层只能在真浏览器和真数据里看见。**

| 问题 | 怎么发现的 | 修法 |
|---|---|---|
| 合规拒绝走 422，界面上的内联拒绝卡片成了死代码，理由被丢到页面顶部的通用横幅 | 浏览器里真提交一句违规要求 | 统一成 200 + `refused`，与模型侧拒绝同一条通道；被拒提案照样存档 |
| 保存新标准后顶部一直显示旧版本号 | 读代码时发现"数据变更后刷新"没重拉标准 | 抽 `reloadToken`，三份数据一起重拉 |
| 一次写事务 76ms（只测了读就下结论，写没测） | 一条并发集成测试偶发 `database is locked` | 日志模式改 TRUNCATE，见 `store/db.py` 的对照表 |
| `TRUNCATE` 非持久化，每个新连接静默退回 DELETE | 修改后测试仍失败，追下去才发现"设置成功"只对当时那个连接成立 | `connect()` 里每连接设一次 |
| 演示脚本按整个 prompt 匹配意图，"提高权重"被识别成"删掉学历门槛" | 看生效后的截图：必须项 1 → 0 | 从 prompt 里切出 HR 原话再分支（prompt 里含当前标准 JSON，里面本来就有"本科"） |
| 改动理由 / 拒绝文案在界面上重复渲染两遍 | 看截图 | 已有的不再重复渲染 |

## 12. 风险与应对

| 风险 | 等级 | 应对 |
|---|---|---|
| **等待时间超过用户忍耐** | 高 | §6 的上传与处理分离 + §2.4 并发 + 已有解析缓存；M8 必须出真实数字 |
| **进程内队列的可靠性** | 中 | 状态落库 + 启动时重置滞留任务（§4.2） |
| **自然语言改标准误改** | 中 | §7 三段式 + 版本可回退 |
| **合规从对话入口泄漏** | 高 | §7 输入侧与输出侧各拦一次 |
| **前端工程量膨胀** | 中 | 不引 UI 库与状态库；M7 只做 P0 的四个部件 |
| **解析质量** | 高 | 沿用 v0.1 的质量自检 + 手工粘贴兜底；解析器保持纯函数 |
| **中文 PDF 版式产生新特例** | 高 | 解析器是纯函数，加特例不影响其他模块；M6 起用真实样本回归 |
