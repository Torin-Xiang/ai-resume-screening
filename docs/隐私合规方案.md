# 候选人数据不出域方案

> 版本 **v2.1** ｜ 2026-10-18 ｜ 状态：待确认硬件 + 待确认公司是否有内网模型网关
> **v2.0 推翻了 v1.0 的主体思路。** v1 做的是"合规文书体系 + 处处设卡"，被判定为本末倒置；v2 只做一件事——**让简历不出这台电脑（或公司域）**。修订记录见文末。
> 本文不写代码。

---

## 0. 结论先说

**一、会上传，而且是全文。** 不是"可能"，是每次处理必然发生。见 §1.1。

**二、能断，而且不用改代码。** 现有架构已经支持，换本地模型只改 `.env` 四行。见 §4。

**三、代价全在速度和质量上，不在功能上。** 这是唯一真正的取舍，必须实测，不能拍脑袋。见 §4.4。

---

## 1. 三个事实问题

### 1.1 现在会不会上传到云端？——会，发的是整份原文

不是推测，指得到代码：

| 环节 | 位置 | 发出去的内容 |
|---|---|---|
| 结构化提取 | `core/prompts.py::EXTRACT_USER_TEMPLATE` | **整份 `raw_text`**，含姓名、手机、邮箱，以及 PDF 里的每一个字 |
| 软性维度评分 | `core/prompts.py::SCORE_USER_TEMPLATE` | **又是整份 `raw_text`** |
| 改标准后重评 | 同上，每份简历再跑一遍 | **再发一遍** |

端点由 `.env` 决定，当前是 `LLM_PROVIDER=deepseek` → `https://api.deepseek.com/v1`。

所以一份简历的一生，外发次数是 **`1 + N`**（N = HR 改标准的次数）。
传输走 HTTPS，链路上是加密的；但**内容对服务商是明文可见的**，是否留存取决于它的条款。这就是"泄露给外人"的全部含义。

### 1.2 敏感字段判定要不要 AI 读一遍？——不要，必须是本地规则

你这个问题问得对，而且我 v1 的写法有毛病：只说了"本地剥离"，没说清"谁在判断"。如果判断要靠模型，逻辑立刻自相矛盾——为了防泄漏，先把简历发出去问一句"这里面有没有身份证号"。

正确做法：**敏感字段识别是纯本地正则/词典扫描，零 API 调用。** 它在本机内存里过一遍，不回传任何东西。所以"读了一遍"这件事本身不构成泄漏——**只要读它的程序不联网**。

但你真正指出的是更根本的一层：**既然最后都要靠本地代码处理，那"本地脱敏"就是绕路。** 这个判断成立。

脱敏解决的是"发出去的内容少一点"，而你要的是"一个字都不发"。两者不是程度差别，是目标差别。**只要还在调云端 API，脱敏就只是把风险从 100 降到 30，永远到不了 0。** 所以 v2 不再以脱敏为主线。

### 1.3 "不外泄"的边界在哪？——只挡第三方，不挡企业内部

你这句话是对的，v1 把它搞错了：

> 我们需要的是尽量不把候选人信息泄露给"外人"，而不是不能保存在企业内部。就算是正常简历筛选，简历在企业内部也不是什么秘密，比如公司人才库，HR 都能看到。

这句话直接推翻了 v1 的四个支柱。风险模型应该这样重画：

| 风险 | 是否真风险 | v1 的判断 | v2 的判断 |
|---|---|---|---|
| 简历存在本机/公司人才库 | **不是风险** | 当成风险（设 TTL、加密） | 不是风险，正常业务数据 |
| 本公司 HR 看到候选人信息 | **不是风险** | 当成风险（审计留痕） | 不是风险，本来就该看到 |
| **简历被发给第三方模型服务商** | **是唯一的核心风险** | 混在一堆措施里 | **唯一靶心** |
| 设备丢失 | 低概率、低影响 | 当成高优先级 | 次要，有了加密更好，没有也不致命 |

**靶心收窄成一件事**：那根从本机连到 `api.deepseek.com` 的线。

整个方案因此缩成一句话：**切断那根线。**

## 2. 为什么"少发一点"不是好答案

如果只在发出去的内容上做减法（去姓名、去身份证号），会同时付出两个代价、只换来半个结果：

- **代价一：准确率。** 少给模型上下文，判断就会漏。你想省的那点字，正好是模型用来判断"这个项目到底算不算 AI 经验"的依据。
- **代价二：效率。** 多一道本地处理、多一层映射还原、多一个可能出错的环节。
- **换来的结果：** 简历还是出域了。只是出得少一点。

**用准确率和效率去换"风险从 100 降到 30"，这笔账不划算。** 把风险降到 0，才值得付代价。

所以顺序应该反过来：**先想办法不出域；实在不行，再退回脱敏。**

## 3. 三条路径，代价摊开

| | **路径 A：本地模型** | **路径 B：公司内网模型网关** | **路径 C：脱敏后调云端** |
|---|---|---|---|
| 数据出域 | **零** | **零**（出本机，不出公司域） | 出域，内容减少 |
| 需要改代码 | **不需要**（只改 `.env`） | 不需要 | 需要（新增脱敏层 + 还原层） |
| 速度 | 慢，取决于硬件 | 取决于网关 | 与现在相同 |
| 准确率 | **会降，降多少未知** | **若为 70B 级则接近云端** | 略降 |
| 一次性成本 | 装 Ollama + 下模型（约 5–20GB） | 需要有网关 | 开发工作量最大 |
| 适用前提 | 本机有可用算力 | 公司已有 LLM 服务 | 无法本地部署时 |

**推荐顺序：先问 B，再试 A。** 如果公司内网已经有模型服务，**B 是最优解，不是备选**——它同时满足"零出域"和"能力不掉"，见 §3.2。只有在公司没有网关时，才退到 A。

### 3.1 "不出域"不等于"用离线模式"——这两件事差了一个数量级

这是最容易混淆的一处，必须单独说清。

**`scripted`（离线模式）不是模型。** `adapters/llm/scripted.py` 第一行就写明："**它不是模型**。所有字段与判定都由确定性规则（正则 / 关键词 / JD 原文匹配）得出，不具备任何语义理解能力。"

它存在的理由是"没密钥时看完整链路与输出形态"，文档里专门警告："看格式，不要把内容当结论。"

而"本地模型"是真的模型推理，只是跑在你自己的机器上。两者不是"准确率差一点"的关系，是**"有没有理解能力"**的关系。

| 层级 | 是什么 | 语义理解 | 9 字段提取 | 软性维度判定 | 数据出域 |
|---|---|---|---|---|---|
| **scripted**（离线模式） | 正则 + 关键词，**不是模型** | **无** | 显式字段尚可（姓名/电话/学校本来就是正则能抓的） | **接近瞎判** | 不出 |
| 本机 7B–8B | 真模型（量化） | 有，但弱 | 中等 | 不稳，易改写原文 | 不出 |
| 本机 14B–32B | 真模型 | 可用 | 较好 | 可用，但必须实测 | 不出 |
| **公司内网 70B 级** | 真模型 | **接近云端** | 好 | 好 | **不出公司域** |
| DeepSeek API（现状） | 云端满血 | 强 | 好 | 好 | **出域** |

**一个必须点明的危险**：`scripted` 的 quote 是**真的**（从原文截取的逐字子串，能通过反编造校验），但它的**判定是假的**。所以它输出的东西"看起来完全正常"——格式对、引用真、三分组也有——只是那些结论没有任何理解支撑。

这比直接报错危险得多，和项目之前踩过的那个坑是同一类：扫描件被判成 `SUSPECT` 仍送模型 → 模型对着水印编字段 → 界面显示"处理成功"但全是编造。**"看起来成功"永远比"明确失败"更危险。**

所以：**离线模式可以用来验收界面，绝不能用来判断准确率。** 这两件事在这个项目里已经混过一次，别再混第二次。

### 3.2 路径 B：能连，怎么连，要问公司什么

**能。** 技术上就是改 `LLM_BASE_URL` 指向公司的端点，代码不用动——因为这条通道本来就叫"通用 OpenAI 兼容（自建网关 / vLLM / 其他厂商）"。

而且这是**唯一同时做到"零出域"和"能力不掉"的方案**。数据出了你的电脑，但没出公司的域。这正是你说的那个边界。

**需要向公司 IT / AI 平台方确认七件事**（按"卡住就做不了"的顺序排）：

| # | 要问的 | 为什么关键 |
|---|---|---|
| 1 | 端点是不是 **OpenAI 兼容**的 `/v1/chat/completions`？ | 兼容的：vLLM、Xinference、One-API / New-API、FastChat、Ollama、多数企业 AI 中台。**Azure OpenAI 不兼容**——它用 `api-key` 头而不是 `Authorization: Bearer`，当前客户端直连会失败 |
| 2 | 鉴权方式：Bearer token？还是要额外 header？ | 当前代码**只支持 `api_key`（走 Bearer），不支持自定义 header**。若网关要 `X-Tenant-Id` 之类，需要小改 |
| 3 | 部署的**模型名**是什么？（`LLM_MODEL` 要填这个） | 填错会 404，报错信息通常只说模型不存在 |
| 4 | **上下文长度**多大？ | 简历常 5000–10000 字，上下文至少 8K，最好 32K。短了会静默截断，抽出来的字段莫名其妙地少 |
| 5 | 是否支持 `response_format: {"type":"json_object"}`？ | 不支持也能凑合——代码里 `parse_json_payload` 会剥掉 ` ```json ` 包裹。但完全吐不出 JSON 就不行 |
| 6 | 网络：内网 / VPN？要不要 IP 白名单？人均 QPS 多少？ | 有限流就会拖慢并发处理，表现为"卡住"而不是报错 |
| 7 | **合规审批**：公司允许把候选人简历喂给内部模型吗？ | 这条通常比技术更难，也最容易被忽略。内部模型往往也有"不得处理个人信息"的内部规定 |

第 7 条是现实约束：很多公司的内网模型只批给"非个人信息"场景。**如果卡在这里，技术上能连也没用**——所以这件事应该先去问，而不是先动手配。

## 4. 路径 A：现有代码已经支持，只改配置

### 4.1 为什么是"零代码"

`adapters/llm/factory.py` 里 `PROVIDER_OPENAI` 的注释原文就是：

> 通用 OpenAI 兼容（自建网关 / vLLM / 其他厂商）

`base_url` 完全由 `LLM_BASE_URL` 决定，代码里**没有任何域名限制**。而 Ollama 提供 OpenAI 兼容端点。所以链路天然是通的——这本来就是当初把通道通用化留下的口子。

（顺带认个错：v1 提的"境内地址白名单"如果照字面实现，会把 `http://127.0.0.1:11434` 一起挡在门外，**为了合规做的措施反而挡住了唯一真正合规的方案**。这条已撤销。）

### 4.2 具体怎么改（四行）

```
LLM_PROVIDER=openai
LLM_BASE_URL=http://127.0.0.1:11434/v1
LLM_MODEL=qwen2.5:14b-instruct
LLM_API_KEY=local
```

`LLM_API_KEY` 那行不是多余：`OpenAICompatClient.__init__` 里 **密钥为空会直接抛 `MissingAPIKeyError`**，本地模型不需要密钥，但要填个占位值把这道校验过掉。

### 4.3 验证方法：拔网线

这是最硬的证据，比读代码可信：

1. 改完配置，**断开网络**（或关掉 Wi-Fi）；
2. 上传一份真实简历，跑到出结果；
3. 能出结果 → 数据零外发，证毕；
4. 报连接错误 → 说明还有个地方在往外发，顺着报错找。

建议把这个做成一个固定动作：每次换模型配置后，都断网跑一遍。**"以为改了配置、其实没生效"是这个项目已经踩过的坑**（`.env` 曾因为入口指向 `:app` 而从未被加载），断网测试能一次性证伪这类问题。

### 4.4 会踩的五个坑（从代码里读出来的，不是猜的）

| # | 坑 | 后果 | 处理 |
|---|---|---|---|
| 1 | `timeout=60.0` | 本地大模型处理长简历会超过 60 秒 | 可能超时失败。**这是唯一可能必须改代码的地方**，或换更小模型 |
| 2 | `max_retries=3` | 超时后重试三次 → 实际耗时 ×3 | 表现是"卡很久然后失败"，不是立刻报错 |
| 3 | `response_format={"type":"json_object"}` | 部分本地模型不支持，直接 400 | 选支持 JSON 模式的模型；不行就要改这行 |
| 4 | `api_key` 必填非空 | 不填就抛错，报错信息会让人误以为要买密钥 | 填 `local` |
| 5 | **证据引用靠模型"抄原文"** | 小模型会**改写**原文而不是逐字复制 → "每条结论带原文引用"的地基塌了 | 见下 |

**第 5 条是本地模型路线最大的风险，比速度更严重。**

产品的核心卖点是"每条结论都能指回原文"。这个能力现在依赖模型老实抄写——大模型基本做得到，7B/14B 级别经常做不到，它会"总结"成一句像原文的话。

一个不依赖模型能力的解法：**让模型只输出判定和关键词，原文片段由本地代码去 `raw_text` 里字符串定位并截取。** 这样 quote 一定逐字，因为它是切出来的，不是生成的。

这条属于改代码，现在不做，但**如果决定走本地模型，这是必须补的一块**。否则准确率可能没掉，可信度先掉了——而可信度是这个产品存在的理由。

### 4.5 速度与准确率：现在给不出数字，必须实测

诚实说：**不知道会掉多少。** 而且有个前提问题——**当前连 DeepSeek 的准确率都还没测出来**（账户余额 0，M8 一直卡着）。所以本地模型只会让这个空白更大，不会更小。

唯一能确定的结构性事实是：**硬门槛（学历/年限/专业/地点/跳槽频次）走规则判定，不经过模型。** 所以即使模型变弱，这五项仍然准。会掉的只有软性维度（"有没有 AI 项目经验"这类口径判断）。

这构成本地路线的兜底：**核心筛选不会崩，只是加分项和减分项的判断变粗。** 是否可接受，取决于你对"软性维度"的依赖程度。

## 5. 复核：v1 哪些措施被撤回

逐条给结论。判据只有一条：**它是否降低效率、准确率或稳定性。**

| v1 措施 | 对效率 | 对准确率 | 裁决 |
|---|---|---|---|
| 姓名替换为 `C-001` | 中性（展示层还原即可） | 零影响 | **撤回**。本地部署后模型看到姓名也无害，没必要多一层映射 |
| 敏感字段不落库 | 中性 | 零影响 | **撤回**。内部保留完整内容便于复核，删了反而伤体验 |
| 扫描件图像不外发 | 中性 | 零影响 | **保留**（本地部署后自动满足） |
| **评分只送"字段 + 片段"** | 增加实现复杂度 | **显著伤准确率** | **撤回**。这是 v1 最严重的错误——为省 token 砍上下文，正好砍在判断依据上 |
| **原文 30 天强制销毁** | **伤效率**：面试中途原文没了 | 间接伤（复核无依据） | **撤回**。改为"提供一键清理入口，不强制、不自动" |
| 落盘加密 | 轻微 | 无 | **降级**。不解决核心矛盾，有余力再做 |
| `--lan` 强制口令 | 一次性配置 | 无 | **保留**（成本几乎为零）。但若只在本机用，可以不启用 |
| 五类动作审计日志 | 轻微 | 无 | **撤回**。内部自用，没有审计对象 |
| **告知书模板 + 逐份声明** | **伤效率**：HR 每份都要点 | 无 | **删除**。见下 |
| **PIA 报告** | 不影响日常 | 无 | **删除**（本阶段） |
| 境内地址白名单 | 无 | 无 | **反向重写**：白名单要允许 `127.0.0.1` 与内网段，否则挡住本地部署 |

**关于告知书那一条，我认错得具体一点：**

v1 写"内置告知书模板"，本意是"公司招聘页上贴一次"，但表述上落成了"每份简历都要给个声明"，这是设计上的失败——**它把一个一次性动作写成了逐份动作，等于给 HR 新增了一道重复劳动，正好违反这个产品存在的理由。**

现实里这件事早就被解决了：企业在招聘平台发岗位时，平台侧本来就有个人信息处理声明，候选人投递即视为知悉。**这是企业已有的基础设施，工具不需要重复造一遍，更不该把成本转嫁给 HR。**

PIA 同理：它是**一次性文档**，做了也不影响日常效率——但它不解决"简历出不出域"，属于"如果想对外售卖时才需要"的东西。本阶段砍掉，不做无用功。

## 6. 如果本地模型不可行，退路顺序

按"代价从小到大"排，不要跳步：

1. **先试小模型**（7B/8B）。速度够用就行，准确率用规则兜底。
2. **问公司有没有内网 LLM 网关**。如果有，`base_url` 指过去，比本地模型更好，可能一步到位。
3. **混合模式**：本地模型做提取（重活，产出结构化字段），云端只做评分（只发字段，不发原文）。仍然出域，但内容是字段而不是整份简历，风险大幅下降。**这是退路，不是目标**——不要一开始就妥协到这里。
4. **最后才是脱敏 + 云端**。到这一步说明前三条都不通，此时才值得付"准确率下降"的代价。

## 7. 需要你确认的两件事

**第一，机器配置。** 这决定本地模型能跑多大、快不快：

| 配置 | 能跑 | 一份简历大致耗时 | 判断 |
|---|---|---|---|
| 无独显，16GB 内存 | 7B/8B 量化 | 1–3 分钟 | 能用，但"来一份看一份"的体验会打折 |
| 8GB 显存 | 7B/8B | 10–20 秒 | 可接受 |
| 12–16GB 显存 | 14B 量化 | 15–30 秒 | 较好 |
| 24GB+ 显存 | 32B 量化 | 20–40 秒 | 接近云端质量 |
| Apple Silicon 32GB+ | 14B–32B | 20–40 秒 | 可接受 |

（耗时是量级估计，不是实测值。）

**第二，能接受多大程度的降级。** 具体是：如果软性维度的判断变粗（比如"有 AI 项目经验"这类口径判断容易误判），但硬门槛（学历/年限/专业/地点）仍然准确，这个产品还能不能用？

这个问题的答案决定本地路线是不是真的可行。**如果答案是"软性判断必须准"，那本地模型大概率不够，只能走路径 B（公司网关）。**
