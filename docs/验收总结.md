## 二、真实浏览器验收记录（M6/M7/M9/M10）

用 `scripts/offline_demo.py` + `web/e2e/ui-smoke.mjs` 在真实 Chrome（独立 profile、
`--headless=new`）里跑完整链路。这个脚本的存在理由：HTTP 层测试全绿**不代表界面能看**——
M7 就踩过一次，接口全部 200、响应 15–26ms，但页面白屏。

### 验的是什么

| 场景 | 操作 | 观察到的结果 |
|---|---|---|
| 三分组 | 灌入 3 份合成简历 | 推荐 1 / 待确认 1 / 不推荐 1 |
| 分组语义 | 王示例（本科+命中加分项）、李示例（**简历未写学历**）、赵示例（大专） | 分别落「推荐」「「本科及以上」简历未提及，待确认」「「本科及以上」不满足：大专」——**未提及与不满足分到两组** |
| 对话式改标准 | 输入"学历不卡了"→ 提交 | 清单显示「删除 必须项「本科及以上」」+ 理由；影响预估「推荐 1→3、待确认 1→0、不推荐 1→0」并列出会动的两份简历 |
| 确认生效 | 点「确认生效（全部采纳）」 | 标准变 `v1-2`、必须项归零、三份全部升到推荐；提示"重排了 3 份简历（未重新解析）" |
| 合规红线 | 输入"把 35 岁以上的候选人筛掉" | 输入框下方内联给出拒绝理由与出路（"可以直接说那件事本身"），**不产生模型调用** |
| 导出 | 点「导出 Excel」 | 无错误横幅；Excel 内容另由接口测试逐格验证 |
| 兜底入口 | 查看上传区 | 「扫描件识别不出来？粘贴简历文本」常驻可见 |

### 这一轮靠验收发现的 7 个问题（测试全绿时它们全都在）

| # | 问题 | 怎么发现的 | 修法 |
|---|---|---|---|
| 1 | 合规拒绝走 HTTP 422，导致界面上的内联拒绝卡片**永远是死代码**，理由被丢到页面顶部的通用错误横幅，离输入框很远 | 浏览器里实际提交一句违规要求 | 统一成 200 + `refused`，与模型侧拒绝同一条通道；被拒的提案照样存档 |
| 2 | 保存新标准后顶部一直显示**旧版本号** | 读代码时发现"数据变更后刷新"只重拉了排名和简历 | 抽 `reloadToken`，让排名/简历/标准三份数据一起重拉 |
| 3 | SQLite 一次写事务要 **76ms**（上一轮只测了读就下了结论，写没测） | 一条并发集成测试偶发 `database is locked`，回头补测写 | 日志模式改 TRUNCATE（8ms）+ 关于写锁与 `BEGIN IMMEDIATE` 的说明 |
| 4 | `TRUNCATE` **不是持久化属性**，只在建库时设一次的话，之后每个新连接都静默退回 DELETE | 修改后测试仍然失败，追下去发现"设置成功"只对当时那个连接成立 | `connect()` 里与 `foreign_keys` 一样每连接设一次 |
| 5 | 演示脚本按**整个 prompt** 匹配改标准意图，于是"提高权重"被识别成"删掉学历门槛"，把必须项删没了 | 看生效后的截图：必须项 1 → 0 | 从 prompt 里切出 HR 原话再分支（prompt 里本来就有当前标准的 JSON，含"本科"字样） |
| 6 | 改动理由在界面上渲染两遍 | 看截图 | `description` 已含理由时不再单独渲染 |
| 7 | 合规拒绝文案重复两遍（标题 + 理由 + 说明段都在说同一件事） | 看截图 | 理由本身已含完整说明，去掉重复的标题与说明段 |

> 这 7 条说明一件事：**"测试全绿"和"能用"之间隔着一层，那层只能在真浏览器和真数据里看见。**
> 第 3 条更说明"只测了一半就下结论"的代价——读写是两件事，测了读不等于测了写。

## 三、阻塞清单（不可虚构，必须补齐）

| # | 阻塞项 | 影响 | 解除条件 | 解除后要做什么 |
|---|---|---|---|---|
| 1 | **3–5 份脱敏真实 PDF 简历** | M1 版式完整性、M2 字段准确率、M4 淘汰认可率、M8 性能实测均无法真实验收 | 业务方提供脱敏样本，放 `fixtures/`（已 gitignore，**不得进 Git**） | 补 `tests/test_real_samples.py`；人工核对文本与 9 字段，统计准确率 ≥ 90% |
| 2 | **`DASHSCOPE_API_KEY`** | M3 无法真实生成、M4 无法真实判定、**M8 整块阻塞** | 在 `.env` 配 `DASHSCOPE_API_KEY=...`（见 `.env.example`） | 跑通真实建岗→生成标准→上传→排名；做"同简历跑 3 次口径是否一致"的检查 |
| 3 | **HR 对评分卡维度的人工评审** | M3 的验收标准本身是主观项 | 1 份真实 JD 生成草稿后由 HR 编辑 | 将评审后的评分卡存入 `rubrics/` 作为团队基线 |
| 4 | **真实批次的"淘汰认可率"** | 方案 §1 的核心成功标准未验证 | 上面 1+2 齐备 | HR 复核一批，统计"AI 淘汰 / HR 认同淘汰"的比例 |
| 5 | **"可接受等待时间"阈值** | 方案 §9 的最大风险（一旦要等就退化成跑批）没有真实数字 | 解除 1+2 | 用真实模型 + 20 份真实简历实测上传到出结论的耗时，据此定并发档位 |

> 测试用 PDF 是**合成夹具**（`tests/conftest.py`、`scripts/offline_demo.py`，均为虚构人物），
> 仅用于验证版式算法与链路，不能替代真实样本。项目内**不存在**任何伪造的简历样本或密钥。

## 四、风险登记（与方案 §9 对齐）

| 风险 | 方案等级 | 当前状态 | 缓解措施 / 待办 |
|---|---|---|---|
| **处理速度**（最大风险） | 高 | 已消除两个数量级的存储层开销（单次写 76ms→8ms、单次读 WAL 75ms→4ms）；上传接口在"上传即返回"上有测试钉住 | 真实模型下的端到端耗时尚无数字（阻塞 #5）；并发档位待实测 |
| PDF 版式千变万化 | 高 | 已按"纯函数 文件路径→ResumeDocument"实现，加特例不会失控；已有分栏/扫描件回归用例 | 真实样本到位后持续补特例，每加一个特例补一个用例 |
| **判定口径漂移**（改标准后结论不一致） | 中 | 影响预估与真实评分**共用同一套分组逻辑**（`verdict_from_dimensions`），不会出现"预估说会升、实际没升"；口径变化一律标"算不准"而不是给近似值 | 需真实数据验证"同简历多次判定是否稳定" |
| 扫描件 / 图片型 PDF | 中 | 自检并标 `needs_manual`，**不送入模型、不静默跳过**；粘贴文本兜底走同一条链路与同一套阈值 | 阈值（200 字 / 中文占比 3%）需按真实样本标定 |
| 合规违规 | 高 | **四层**防护：prompt 显式禁止 → 输出侧清单校验 → 输入侧原话拦截（在调用模型之前）→ 维度构造层校验；含地域歧视召回 7 条与误伤防护 6 条 | 词表需随业务补充；已在浏览器里验证拦截后不产生模型调用 |
| 个人信息泄露 | 中 | `data/`、`fixtures/`、`*.xlsx`、冒烟截图已 gitignore；测试只用合成样本 | 提交前自查 `git status`，真实样本永不上库 |
| **标准被静默改掉** | 中 | 改标准必须走"清单 → 影响 → 确认"，有测试钉住"propose 不改标准"；提案与版本都存档，可回滚 | — |

## 五、已知技术债（与方案 §10 对齐，主动承担）

| 技术债 | 现状 | 迁移成本 |
|---|---|---|
| 单进程（无任务队列） | worker 是进程内线程池，并发即消费者数（默认 5） | 换异步任务队列；`services/worker.py` 已是唯一入口 |
| 写事务进程内串行 | 一把进程内写锁（单机单人的正确选择） | 多进程部署时失效，届时靠 `BEGIN IMMEDIATE` + busy timeout 兜底 |
| 本地 SQLite | `data/app.db` | 换 Postgres 时 `store/` 是唯一入口 |
| 无权限模型 | 单机单人；`--lan` 是共享链接但不隔离数据 | 多人协作时再补（方案明确延后） |
| 版本对比只能肉眼看 | 有历史版本、可回滚，但没有"A/B 两套标准并排比排名"的界面 | 后端已按 `rubric_id` 存结果，加对比视图即可 |
| 缓存与结果无清理策略 | 只增不删 | 需要时加保留策略 |

**明确未做（方案 §5.2 / §8 明确不做，代码库中不存在）**：
登录权限与多人协作、向量库语义搜索、**自动发拒信**（发错撤不回，必须人工发）、面试安排、
题库生成、BI 看板、模型微调、**权重自动学习**（标注数据不足时学出来是噪声，等人工复核攒够
200+ 条再考虑）、备注标签、排名变化提示、批量操作。
