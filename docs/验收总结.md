## 二、阻塞清单（不可虚构，必须补齐）

| # | 阻塞项 | 影响 | 解除条件 | 解除后要做什么 |

| 1 | **3–5 份脱敏真实 PDF 简历** | M1 版式完整性、M2 字段准确率、M4 淘汰认可率均无法真实验收 | 业务方提供脱敏样本，放 `fixtures/`（已 gitignore，**不得进 Git**） | 补 `tests/test_real_samples.py`；人工核对文本与 9 字段，统计准确率 ≥ 90% |
| 2 | **`DASHSCOPE_API_KEY`** | M3 无法真实生成、M4 无法真实判定 | 在 `.env` 配 `DASHSCOPE_API_KEY=...`（见 `.env.example`） | 跑通 `rubric new` + `screen`；做同简历跑 3 次的口径一致性检查 |
| 3 | **HR 对评分卡维度的人工评审** | M3 的验收标准本身是主观项 | 1 份真实 JD 生成草稿后由 HR 编辑 | 将评审后的评分卡作为团队基线存入 `rubrics/` |
| 4 | **真实批次的"淘汰认可率"** | 方案 §1 的核心成功标准未验证 | 上面 1+2 齐备 | HR 复核一批，统计"AI 淘汰 / HR 认同淘汰"的比例 |

## 三、风险登记（与方案 §9 对齐）

| 风险 | 方案等级 | 当前状态 | 缓解措施 / 待办 |
|---|---|---|---|
| PDF 版式千变万化 | 高 | 已按"纯函数 文件路径→ParseResult"实现，加特例不会失控；已有分栏/扫描件回归用例 | 真实样本到位后持续补特例，每加一个特例补一个用例 |
| 扫描件 / 图片型 PDF | 中 | 已实现自检并标记 `needs_manual`，**不送入模型** | 阈值（200 字 / 中文占比 3%）需按真实样本标定 |
| 判定口径不清 | 中 | 维度强制 `definition` + 正反例；软性维度一次性批量判定以稳定口径 | 需真实数据验证"同简历多次判定是否稳定" |
| 合规违规 | 高 | 三层防护：prompt 显式禁止 → 维度构造层拦截 → 输出校验层（理由涉红线即作废） | 已含误报回归（Agent/age）；词表需随业务补充 |
| 个人信息泄露 | 中 | `data/`、`fixtures/`、`*.xlsx` 已 gitignore；测试只用合成样本 | 提交前自查 `git status`，真实样本永不上库 |

## 四、已知技术债（与方案 §10 对齐，MVP 主动承担）

| 技术债 | 现状 | 迁移成本 |
|---|---|---|
| 单进程 CLI | `screen` 顺序处理 | 换异步任务队列；`core/pipeline.py` 已是纯编排，接入成本低 |
| 单 JD | 每次运行一份评分卡 | 已预留 `run_id`，评分卡带 `version`；多岗位需引入 `job_id` |
| 本地 JSON 存储 | `data/cache`、`data/runs` | 换 SQLite：`ResumeCache` / `run_store` 是唯一入口，替换集中 |
| 无权限模型 | 单机单人使用 | 多人协作时再补 |
| 缓存与结果无清理策略 | 只增不删 | 需要时加 `--purge-cache` 与保留策略 |

**明确未做（方案 §2.2，v1 及以后）**：Web UI / 登录权限、向量库语义搜索、自动发拒信、
面试安排、题库生成、BI 看板、模型微调、权重自动学习、多 JD 管理台。代码库中**不存在**这些功能。
